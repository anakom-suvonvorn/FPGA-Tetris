## 3. กระบวนการหาข้อมูล

### 3.1 การเลือกหัวข้อ

กลุ่มเริ่มจากรวบรวมไอเดียหลายแบบแล้วเปรียบเทียบ ตามเกณฑ์ของงาน (ใช้ FPGA อย่างน้อย 2 บอร์ด,
งานหลักต้องอยู่ใน FPGA, ยากกว่าแลป) และความชอบของกลุ่ม (อยากได้งานที่สนุก เล่นกับเพื่อนได้ และมีมุกมีม)

| ไอเดีย | ข้อดี | ข้อเสีย | ผล |
|---|---|---|---|
| อุปกรณ์ IoT / เครื่องใช้ | มีประโยชน์จริง | งานหลักมักอยู่ที่ไมโครคอนโทรลเลอร์, ไม่สนุก | ไม่เลือก |
| เครื่องเล่นวิดีโอ (Bad Apple) | ท้าทายเรื่องหน่วยความจำ | ใช้บอร์ดเดียว, ดูอย่างเดียว | นำไปเป็นส่วนหนึ่ง |
| เกมยิง 3D แบบ Doom | น่าทึ่ง | ใหญ่เกิน 8,000 LUT มาก | ไม่เลือก |
| **เตตริสต่อสู้ 2 บอร์ด** | ใช้ 2 บอร์ดอย่างมีความหมาย, ทุกคนรู้กติกา, ขยายเพิ่มได้ทีละชั้น | ต้องออกแบบโปรโตคอลเอง | **เลือก** |

ข้อดีที่สำคัญที่สุดของเตตริสต่อสู้คือ **แบ่งเป็นชั้นได้**: ชั้นแรก (เกม + ต่อสู้) ทำเสร็จก็ส่งงานได้แล้ว
ชั้นต่อไป (CHAOS, สื่อจากแฟลช) เพิ่มทีละชั้นเมื่อมีเวลา ทำให้ความเสี่ยงต่ำแต่เพดานสูง

### 3.2 แหล่งข้อมูลที่ศึกษา

| เรื่อง | ศึกษาจาก | นำไปใช้ที่ |
|---|---|---|
| ขาและอุปกรณ์ของบอร์ด | คู่มือบอร์ด, ไฟล์ขาใน FPGA Builder, วงจรทดสอบ 01-05 | `pins.xdc` |
| VGA timing | มาตรฐาน 640 × 480 @ 60 Hz (tinyvga.com) | `vga_sync` |
| UART | หลักการ 8N1, แลปของรายวิชา | `uart_tx`, `uart_rx` |
| SPI flash, STARTUPE2 | datasheet S25FL064L, เอกสาร 7 Series Configuration (UG470) | `spi_flash` |
| Block RAM | 7 Series Memory Resources (UG473) | `media_engine` |
| กติกาเตตริส | Tetris Guideline (tetris.wiki) | `tetris_core` |
| IMA ADPCM | เอกสารมาตรฐาน IMA (1992) | `adpcm_dec`, `make_game_media.py` |
| VHDL และ Vivado | เอกสารและแลปของรายวิชา | ทุกไฟล์ |

### 3.3 ข้อจำกัดที่กำหนดทิศทางการออกแบบ

1. **ไม่มี RAM ภายนอก** มีแค่ block RAM 45 KB ในชิป: ภาพ 640 × 480 เต็มจอ (12 บิต) ต้องใช้ 450 KB
   จึงเก็บภาพทั้งจอไม่ได้ → ภาพเกม **คำนวณสดทุกพิกเซล** (ไม่มี frame buffer) และวิดีโอลดเป็น 160 × 120
2. **LUT 8,000 ตัว**: ทุกฟีเจอร์ต้องคุ้ม เช่น ใช้ตัวตรวจการชนตัวเดียวร่วมกันทุกขั้น, ใช้ ROM ฟอนต์ตัวเดียวร่วมกันทุกบรรทัดข้อความ
3. **แฟลช 8 MB** อ่านได้ประมาณ 3.1 MB/วินาที: พอสำหรับวิดีโอที่บีบอัดแล้ว แต่ไม่พอสำหรับภาพดิบ
4. **ไม่มีวงจรเสียง (DAC)** ต่อกับช่องหูฟัง: ใช้ sigma-delta แทน
5. **VHDL-93**: FPGA Builder ของ TA อ่านเป็น VHDL-93 จึงใช้ไวยากรณ์ใหม่บางอย่างไม่ได้

## 4. การออกแบบ (Top-Down Design)

**Top-Down** คือเริ่มออกแบบจากภาพรวมก่อน แล้วแบ่งเป็นส่วนย่อยทีละระดับ จนแต่ละส่วนเล็กพอจะเขียนเป็นโมดูล VHDL
ที่ทำงานเดียวและทดสอบแยกได้ บทนี้เรียงตามระดับ: ระดับ 0 ระบบทั้งหมด → ระดับ 1 วงจรในหนึ่งบอร์ด →
ระดับ 2 การต่อสายระหว่างโมดูล → ระดับ 3 ข้างในแต่ละโมดูล

### 4.1 ข้อกำหนดของระบบ (Requirements)

| รหัส | ข้อกำหนด |
|---|---|
| R1 | เล่นเตตริสได้ครบตามกติกาสมัยใหม่ บนจอ VGA ด้วยปุ่มบนบอร์ด |
| R2 | สองบอร์ดเล่นต่อสู้กันได้: ส่งขยะ, เห็นสถานะคู่แข่ง, เริ่มพร้อมกัน, ตัดสินผลตรงกัน |
| R3 | รู้ได้ว่าสายเชื่อมต่ออยู่หรือไม่ และเล่นคนเดียวได้เมื่อไม่มีคู่ |
| R4 | โหมด CHAOS: ภารกิจด้วยสวิตช์ → การโจมตีหรือโบนัส |
| R5 | เพลงและเสียงเอฟเฟกต์ระหว่างเล่น |
| R6 | วิดีโอพร้อมเสียงจากแฟลช: การโจมตี, ฉากชนะ/แพ้, sprite |
| R7 | วงจรทั้งหมดใส่ในชิป XC7S15 ได้ และผ่าน timing ที่ 50 MHz |

### 4.2 ระดับ 0: ระบบทั้งหมด

![ระดับ 0: บอร์ดสองบอร์ด เชื่อมด้วยสาย 3 เส้น แต่ละบอร์ดมีจอ หูฟัง และชิปแฟลช](../figures/fig_system.png)

ระบบประกอบด้วยบอร์ดสองบอร์ดที่ **โหลดวงจรเดียวกันทุกบิต** (ไฟล์ `top_tetris.bit` ไฟล์เดียว)
ไม่มีบอร์ดหลัก/บอร์ดรอง ทั้งสองบอร์ดเท่ากัน เหตุผล:

* ไม่ต้องสร้างและโหลดไฟล์สองแบบ ลดโอกาสผิดพลาด
* กติกาตัดสินถูกออกแบบให้ทั้งสองฝั่งคำนวณได้ผลเดียวกันเองโดยไม่ต้องถามกัน (ข้อ 4.7.6)

**สายเชื่อม**: ใช้สายจัมเปอร์ตัวเมีย-ตัวเมีย 3 เส้น **ต่อตรงจากขาถึงขา** ไม่มีอุปกรณ์อื่นคั่น
(ขาของทั้งสองบอร์ดเป็นสัญญาณ 3.3 V เหมือนกัน เอาต์พุตของบอร์ดหนึ่งจึงขับอินพุตของอีกบอร์ดได้โดยตรง):

| บอร์ด A | | บอร์ด B |
|---|---|---|
| J5 ขา 5 (L14, `link_tx`) | → | J5 ขา 6 (M13, `link_rx`) |
| J5 ขา 6 (M13, `link_rx`) | ← | J5 ขา 5 (L14, `link_tx`) |
| J5 ขา 2 (GND) | — | J5 ขา 2 (GND) |

สาย TX ของบอร์ดหนึ่งต้องไปที่ RX ของอีกบอร์ด (ไขว้กัน) ห้ามต่อ TX ชน TX และต้องต่อกราวด์ร่วมกัน
เพราะแรงดัน "0" กับ "1" วัดเทียบกับกราวด์ ถ้าไม่ต่อกราวด์ ฝั่งรับจะแยก 0 กับ 1 ไม่ออก

### 4.3 ระดับ 1: วงจรในหนึ่งบอร์ด แบ่งเป็นกลุ่มหน้าที่

![โครงสร้างลำดับชั้นของการออกแบบ (ระดับ 0 ถึง 3)](../figures/fig_hierarchy.png)

วงจรบนบอร์ดหนึ่งคือ entity `top_tetris` (ไฟล์ `game/top_tetris.vhd`) ซึ่งแบ่งเป็น 7 กลุ่มหน้าที่
แต่ละกลุ่มแบ่งต่อเป็นโมดูล VHDL ที่มีหน้าที่ชัดเจนเพียงอย่างเดียว ทดสอบแยกได้ และต่อกันผ่าน port เท่านั้น:

| กลุ่ม | โมดูล (ชื่อ instance ใน top_tetris) | ไฟล์ | หน้าที่ |
|---|---|---|---|
| ภาพ: จังหวะ | `vga_sync` (`u_sync`) | `src/common/vga_sync.vhd` | ตำแหน่งพิกเซล x, y และ frame_tick |
| อินพุต | `tetris_input` (`u_input`) → `debounce` × 5 (`u_db`) | `src/game/tetris_input.vhd`, `src/common/debounce.vhd` | ปุ่ม → คำสั่ง 1 รอบนาฬิกา |
| อินพุต | `switch_filter` (`u_sw`) | `src/common/switch_filter.vhd` | กรองสวิตช์เลื่อน 13 ตัว |
| กติกาเกม | `tetris_core` (`u_core`) | `src/game/tetris_core.vhd` | กระดาน, บล็อก, ตรวจชน, ล้างแถว, ขยะ |
| การสื่อสาร | `versus_link` (`u_link`) → `uart_tx` (`u_tx`), `uart_rx` (`u_rx`) | `src/game/versus_link.vhd`, `src/common/uart_*.vhd` | เหตุการณ์ ↔ ไบต์บนสาย |
| CHAOS | `chaos_task` (`u_task`), `chaos_fx` (`u_fx`), `chaos_render` (`u_crender`) → `text_multi` (`u_text`) | `src/game/chaos_*.vhd` | ภารกิจ, ผลการโจมตี, ภาพของ CHAOS |
| ภาพ: วาด | `tetris_render` (`u_render`) → `text_multi` (`u_text`), `media_mix` (`u_mix`) | `src/game/tetris_render.vhd`, `src/media/media_mix.vhd` | คำนวณสีทุกพิกเซล |
| สื่อจากแฟลช | `media_ctrl` (`u_mctrl`), `media_engine` (`u_media`) → `spi_flash` (`u_spi`), `adpcm_dec` (`u_dec`), `STARTUPE2` | `src/media/*.vhd` | เลือกและเล่นวิดีโอ/เพลง |
| เสียง + ตัวเลข | `tetris_sound` (`u_sound`), `seg7_scan` (`u_seg`) | `src/game/tetris_sound.vhd`, `src/common/seg7_scan.vhd` | ผสมเสียงออกหูฟัง, แสดงตัวเลข |

ค่าที่หลายโมดูลใช้ร่วมกันเก็บไว้ใน **package** 4 ไฟล์: `common_pkg` (ค่าคงที่ของบอร์ด เช่น CLKS_PER_BIT = 434, ฟอนต์ 7-segment),
`tetris_pkg` (ขนาดกระดาน, รูปทรงบล็อก 7 แบบ × 4 การหมุน, สี, ตารางความเร็ว), `text_pkg` (ฟอนต์ 5 × 7 ที่ออกแบบเอง 64 ตัวอักษร),
`chaos_pkg` (รายการภารกิจ, การโจมตี, ช่วงเวลาสุ่ม, ข้อความแบนเนอร์)

### 4.4 ระดับ 2: การต่อสายระหว่างโมดูล

![การไหลของข้อมูลระหว่างโมดูล: ทุกเส้นคือกลุ่มสัญญาณจริงใน port map ของ top_tetris (สีของเส้น = กลุ่มของโมดูลต้นทาง)](../figures/fig_blocks.png)

อ่านแผนภาพจากซ้าย (อินพุต) ไปขวา (เอาต์พุต) เป็น 3 แถว:

1. **แถวบน (เกม)**: ปุ่ม → `tetris_input` → ตัวกรองปุ่ม (MIRROR/LOCK) → `tetris_core` → `tetris_render` → `media_mix` → จอ
2. **แถวกลาง (CHAOS)**: สวิตช์ → `switch_filter` → `chaos_task` → `chaos_fx` → `chaos_render` → (overlay เข้า `tetris_render`)
   โดย `chaos_fx` ส่งผลของการโจมตีขึ้นไปที่ `tetris_core` (ผลต่อเกม), `tetris_render` (FLIP, BLIND) และตัวกรองปุ่ม (MIRROR, LOCK)
3. **แถวล่าง (สาย + สื่อ)**: `versus_link` คุยกับอีกบอร์ดผ่าน J5 และส่ง/รับเหตุการณ์กับ `tetris_core`, `chaos_task`, `chaos_fx`, `tetris_render`
   ส่วน `media_ctrl` สั่ง `media_engine` ให้อ่านแฟลช แล้วส่งภาพไป `media_mix` และเสียงไป `tetris_sound`

### 4.6 กฎการออกแบบที่ใช้ทุกไฟล์

1. **นาฬิกาเดียว (50 MHz)**: สิ่งที่ช้ากว่าใช้ "enable pulse" ยาว 1 รอบนาฬิกา (เช่น `frame_tick`) แทนการหารนาฬิกา
   เหตุผล: นาฬิกาที่หารเองทำให้ Vivado วิเคราะห์ timing ไม่ได้ และข้ามโดเมนนาฬิกายาก
2. **ทุกอินพุตจากภายนอกผ่าน flip-flop 2 ตัว** (synchronizer) ก่อนใช้ เพื่อกัน metastability
   (ปุ่ม, สวิตช์, สาย RX, ขาข้อมูลจากแฟลช)
3. **ไม่มี reset แยก**: ทุกรีจิสเตอร์มีค่าเริ่มต้นใน `signal ... := ...` ซึ่ง FPGA โหลดให้ตอนเปิดเครื่อง
4. **VHDL-93 เท่านั้น** เพื่อให้ใช้กับ FPGA Builder ของ TA ได้
5. **ทุกไฟล์ขึ้นต้นด้วยคำอธิบาย** ว่าโมดูลทำอะไร ทำอย่างไร และใช้เวลากี่รอบนาฬิกา

#### 4.7.1 `vga_sync`: ตำแหน่งพิกเซลและจังหวะเฟรม

**หน้าที่**: บอกทุกโมดูลว่า "ตอนนี้จอกำลังวาดพิกเซลไหน" (x, y) และสร้างพัลส์ HSYNC, VSYNC ให้จอ

| port | ทิศ | ความหมาย |
|---|---|---|
| `clk` | in | 50 MHz |
| `x` (0-799), `y` (0-524) | out | ตำแหน่งปัจจุบัน (รวมช่วงซ่อน) |
| `video_on` | out | 1 เมื่อ x < 640 และ y < 480 (นอกนั้นต้องส่งสีดำ) |
| `hsync`, `vsync` | out | พัลส์ sync (active-low) |
| `frame_tick` | out | 1 หนึ่งรอบนาฬิกาต่อเฟรม ตอนวาดส่วนที่มองเห็นเสร็จ |

**วิธีทำงาน**:

1. `half` สลับ 0/1 ทุกรอบนาฬิกา ตัวนับเดินเฉพาะรอบที่ `half = '1'` จึงได้อัตรา 25 MHz โดยไม่ต้องสร้างนาฬิกาใหม่
2. `hc` นับ 0 ถึง 799 แล้วกลับเป็น 0 ทุกครั้งที่กลับเป็น 0 `vc` เพิ่ม 1 (นับ 0 ถึง 524)
3. hsync เป็น 0 ขณะ `hc` อยู่ในช่วง 656-751 (640 + 16 ถึง 640 + 16 + 96 − 1) vsync เป็น 0 ขณะ `vc` = 490-491
4. `frame_tick` เป็น 1 เมื่อบรรทัดที่ 479 (บรรทัดสุดท้ายที่มองเห็น) จบ ซึ่งเป็นต้นช่วงซ่อนแนวตั้ง
   เกมจึงอัปเดตสถานะในช่วงที่จอไม่ได้วาด ภาพไม่ขาดกลางเฟรม

#### 4.7.2 `debounce` และ `tetris_input`: ปุ่มกด → คำสั่ง

**ปัญหาของปุ่มจริง 3 อย่าง** และวิธีแก้ใน `debounce`:

1. ปุ่มเปลี่ยนเมื่อไรก็ได้ ไม่ตรงกับนาฬิกา → ผ่าน flip-flop 2 ตัว (`sync1`, `sync2`)
2. หน้าสัมผัสโลหะเด้ง (bounce) เปิดปิดรัวๆ หลายมิลลิวินาที → ยอมรับค่าใหม่เมื่อค่าคงที่ต่อเนื่อง `STABLE_CYCLES` รอบ
   (top ตั้งไว้ 250,000 รอบ = 5 ms)
3. ต้องการ "กด 1 ครั้ง = 1 คำสั่ง" → `pressed` เป็น 1 หนึ่งรอบนาฬิกาเมื่อค่าที่กรองแล้วเปลี่ยนจาก 0 เป็น 1

**`tetris_input`** วาง `debounce` 5 ตัว (ใช้ `for ... generate`) แล้วเพิ่ม **การกดค้าง (auto-repeat)** แบบเกมเตตริสจริง:

| ปุ่ม | กดครั้งแรก | กดค้าง |
|---|---|---|
| ซ้าย / ขวา | ทำทันที | หลัง 10 เฟรม (DAS) ทำซ้ำทุก 3 เฟรม (ARR) |
| ตกช้า | ทำทันที | ทำซ้ำทุก 2 เฟรม |
| หมุน / ตกทันที | ทำทันที | ไม่ทำซ้ำ (ต้องกดใหม่) |

`held(i)` นับจำนวนเฟรมที่กดค้าง เมื่อถึง `DAS - 1` ก็ส่งคำสั่งแล้วตั้ง `held` เป็น `DAS - ARR` เพื่อให้ครั้งต่อไปมาอีกใน ARR เฟรม

#### 4.7.3 `switch_filter`: กรองสวิตช์เลื่อน

**ปัญหาที่พบจากการทดสอบ**: สวิตช์เลื่อนบนบอร์ดเด้งรุนแรงกว่าปุ่ม และถ้าโยกค้างครึ่งทาง ขาจะลอย (ไม่ได้ต่อทั้ง 0 และ 1) อ่านค่ามั่วได้
ภารกิจ FLIP ("โยกสวิตช์ 10 ครั้ง") จึงนับผิด

**วิธีแก้ 2 ชั้น**:

1. ใน `pins.xdc` ตั้ง `PULLDOWN true` ทุกขาสวิตช์: ขาที่ลอยจะถูกดึงลงเป็น 0 อย่างนิ่ง
2. วงจร **integrator** ต่อสวิตช์: ทุก 1 ms (`TICK_CYCLES` = 50,000) สุ่มอ่านสวิตช์ ตัวนับ 0..10 **นับขึ้นถ้าอ่านได้ 1 นับลงถ้าได้ 0**
   เอาต์พุตเปลี่ยนเป็น 1 เมื่อตัวนับถึง 10 และเป็น 0 เมื่อถึง 0 การเด้งสั้นๆ แค่ทำให้ตัวนับขยับขึ้นลงนิดหน่อย
   ค่าใหม่ผ่านไปได้หลังอ่านค่าเดิมต่อเนื่องประมาณ 10 ms ซึ่งคนไม่รู้สึก

#### 4.7.5 `uart_tx` และ `uart_rx`: ส่ง/รับทีละบิต

**`uart_tx`**: เมื่อได้ `start` เก็บ 10 บิตลงรีจิสเตอร์ `frame = stop & data & start` แล้วส่ง `frame(0)` ออกขา
ทุก 434 รอบนาฬิกาเลื่อน `frame` ไปทางขวา 1 บิต ครบ 10 บิตก็หยุด `busy` เป็น 1 ตลอดการส่ง (87 µs)

<!-- CODE: src/common/uart_tx.vhd | ^begin | busy <= sending -->

**`uart_rx`**: FSM 4 สถานะ

1. **S_IDLE**: รอสายตกเป็น 0 (start bit เริ่ม)
2. **S_START**: รอครึ่งบิต (217 รอบ) ถึงกลาง start bit ถ้ายังเป็น 0 จริงก็ไปต่อ (ถ้าไม่ใช่ = สัญญาณรบกวน กลับ S_IDLE)
3. **S_DATA**: รอทีละ 434 รอบ 8 ครั้ง แต่ละครั้งตรงกลางบิตข้อมูลพอดี เลื่อนบิตเข้าจากด้านซ้ายของ `shreg`
   (บิตต่ำมาก่อน หลัง 8 บิตจึงเรียงถูกที่)
4. **S_STOP**: รออีก 1 บิต ถ้าเป็น 1 (stop bit ถูกต้อง) ส่งไบต์ออกพร้อม `valid = '1'` 1 รอบ ถ้าไม่ใช่ทิ้งไบต์นั้น

#### 4.7.6 `versus_link`: โปรโตคอลระหว่างบอร์ด

![รูปแบบข้อความ 1 ไบต์ สัญญาณบนสาย และกติกาการตัดสิน](../figures/fig_link.png)

**ทำไมใช้ข้อความ 1 ไบต์**: ข้อมูลที่ต้องส่งมีน้อยมาก (จำนวนแถว ≤ 31, ความสูง ≤ 20, หมายเลขการโจมตี ≤ 10)
แบ่งเป็นชนิด 3 บิต + ค่า 5 บิตก็พอ ไม่ต้องมีการต่อข้อความหลายไบต์ ไม่มีปัญหา "ข้อความขาดครึ่ง"
และ 1 ไบต์ส่งเสร็จใน 87 µs เร็วกว่าหนึ่งเฟรมภาพ (16,800 µs) มาก

| ชนิด (บิต 7-5) | ชื่อ | ค่า (บิต 4-0) | ส่งเมื่อ |
|---|---|---|---|
| 000 | HEARTBEAT | ความสูงกองบล็อกของฉัน 0-20 | ทุก 6 เฟรม (10 ครั้งต่อวินาที) |
| 001 | GARBAGE | จำนวนแถวขยะ 1-31 | ล้าง 2-4 แถวพร้อมกัน |
| 010 | LOST | - | ฉันแพ้ (ล้นจอ) |
| 011 | START | - | ฉันกดเริ่มเกม |
| 100 | ATTACK | หมายเลขการโจมตี 0-10 | ทำภารกิจสำเร็จและสุ่มได้การโจมตี |

**ฝั่งส่ง**: คำขอส่ง (`send_*`) อาจมาพร้อมกันหลายอย่าง จึงจำไว้ในรีจิสเตอร์ `*_p` แล้วส่งทีละไบต์เมื่อ `uart_tx` ว่าง
ตามลำดับความสำคัญ **START > LOST > ATTACK > GARBAGE > HEARTBEAT** ขยะที่รอส่งรวมกันได้ (2 + 4 = ส่ง "6" ครั้งเดียว)

**ฝั่งรับ**: ทุกไบต์ที่รับได้ ดูบิต 7-5 แล้วสร้างพัลส์ `got_*` 1 รอบนาฬิกา และตั้งตัวนับ `silence = 0`
ทุกเฟรมที่ไม่มีไบต์มา `silence` เพิ่ม 1 **`link_ok = 1` เมื่อ `silence` < 30** (มีไบต์มาภายใน 0.5 วินาทีล่าสุด)
HEARTBEAT ทำให้มีไบต์มาเสมอ ถ้าถอดสาย `link_ok` จะตกภายในครึ่งวินาทีและเกมเล่นแบบคนเดียว
ความสูงใน HEARTBEAT ยังใช้วาดแถบ RIVAL บนจออีกฝั่งด้วย (ได้สองอย่างในข้อความเดียว)
