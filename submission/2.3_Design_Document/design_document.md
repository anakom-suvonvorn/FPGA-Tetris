# คำนำ

รายงานฉบับนี้จัดทำขึ้นเป็นส่วนหนึ่งของรายวิชา 01076113 Digital System Fundamentals เพื่ออธิบายการออกแบบและพัฒนา
ชิ้นงาน **Tetris Duel: CHAOS Edition** ซึ่งเป็นเกมเตตริสต่อสู้สำหรับผู้เล่นสองคนบนบอร์ด FPGA สองบอร์ด
ครอบคลุมตั้งแต่กระบวนการหาข้อมูล การออกแบบด้วยกระบวนการ Top-Down การพัฒนา การทดสอบ จนถึงวิธีสร้างชิ้นงานซ้ำ

เนื้อหาเริ่มจากพื้นฐานที่จำเป็น แล้วลงรายละเอียดทีละระดับจนถึงโค้ดของแต่ละโมดูล พร้อมเหตุผลของการตัดสินใจออกแบบในแต่ละขั้น
เพื่อให้ผู้อ่าน แม้ไม่เคยใช้ FPGA มาก่อน เข้าใจหลักการและสร้างชิ้นงานนี้ได้เองโดยไม่ต้องสอบถามผู้พัฒนา
ตัวเลขทุกค่าในรายงานมาจากโค้ดจริง ผลการจำลอง (simulation) และรายงานการ build ของ Vivado

คณะผู้จัดทำหวังว่ารายงานฉบับนี้จะเป็นประโยชน์แก่ผู้ที่สนใจการออกแบบระบบดิจิทัลบน FPGA
หากมีข้อผิดพลาดประการใด คณะผู้จัดทำขออภัยมา ณ ที่นี้

# บทคัดย่อ

Tetris Duel: CHAOS Edition เป็นเกมเตตริสแบบต่อสู้สำหรับผู้เล่นสองคน ทำงานบนบอร์ด EDGE Spartan-7 (ชิป XC7S15) สองบอร์ด
ที่เชื่อมกันด้วยสายไฟ 3 เส้น ทุกส่วนของเกม ได้แก่ กติกา ภาพ VGA 640 × 480 เสียง การสื่อสารระหว่างบอร์ด และเครื่องเล่นวิดีโอ
เป็นวงจรดิจิทัลที่เขียนด้วยภาษา VHDL และทำงานใน FPGA ทั้งหมด โดยไม่มี CPU

บอร์ดทั้งสองโหลดวงจรเดียวกันและสื่อสารกันด้วย UART 115,200 bps ผ่านข้อความขนาด 1 ไบต์ เพื่อส่งแถวขยะ ความสูงกอง
การเริ่มเกม และผลแพ้ชนะ ในโหมด CHAOS ผู้เล่นต้องทำภารกิจด้วยสวิตช์เลื่อน 7 แบบระหว่างเล่น เมื่อสำเร็จจะสุ่มได้การโจมตี
จอคู่แข่ง 11 แบบ (โอกาส 62.5 %) หรือโบนัส 3 แบบ (โอกาส 37.5 %) เพลง วิดีโอ และภาพทั้งหมด 6.86 MB เก็บในชิปแฟลช SPI
บนบอร์ด เสียงบีบอัดแบบ IMA ADPCM 16 kHz และภาพวิดีโอ 160 × 120 พิกเซลบีบอัดแบบ delta + run-length

การออกแบบใช้กระบวนการ Top-Down แบ่งวงจรเป็นโมดูล VHDL 25 ไฟล์ (5,705 บรรทัด) ทดสอบด้วย testbench 13 ชุด
และวงจรทดสอบบนฮาร์ดแวร์ 6 ชุด ผลการ build ใช้ LUT 85 % และ block RAM 100 % ของชิป ผ่าน timing ที่ 50 MHz
(WNS +3.441 ns) และเล่นต่อสู้บนบอร์ดจริงสองบอร์ดได้ครบทุกฟังก์ชัน

**คำสำคัญ**: FPGA, Top-Down Design, VHDL, เตตริส, UART, SPI Flash, VGA, ADPCM

## 1. บทนำ

### 1.1 ชิ้นงานคืออะไร

**Tetris Duel: CHAOS Edition** คือเกมเตตริสแบบต่อสู้สำหรับผู้เล่นสองคน ผู้เล่นแต่ละคนใช้บอร์ด EDGE Spartan-7
ของตัวเอง ต่อจอ VGA และหูฟัง บอร์ดทั้งสองเชื่อมกันด้วยสายไฟ 3 เส้น เมื่อผู้เล่นล้างหลายแถวพร้อมกัน
แถวขยะ (garbage) จะถูกส่งไปดันกองบล็อกของคู่แข่งขึ้นมา คนที่อยู่รอดคนสุดท้ายชนะ

ในโหมด **CHAOS** เกมจะสุ่ม "ภารกิจ" ให้ทำด้วยสวิตช์เลื่อนบนบอร์ดระหว่างที่ยังเล่นเตตริสอยู่
ทำสำเร็จแล้วสุ่มต่อ: **โอกาส 62.5 % (5 ใน 8)** ได้โจมตีจอคู่แข่ง (กลับจอ, ซ่อนบล็อก, ลูกบอลเด้งบังจอ, ล็อกปุ่ม ฯลฯ)
และ **โอกาส 37.5 % (3 ใน 8)** ได้โบนัสให้ตัวเอง การโจมตีบางแบบจะเปิด **วิดีโอมีมพร้อมเสียง** (Bad Apple!!, OIIA OIIA, Jevil)
เป็นพื้นหลังของจอคู่แข่ง เกมยังมีเพลงประกอบ, คลิปตอนชนะ/แพ้ และตัวละครลอยบนจอ ทั้งหมดเก็บไว้ในชิปแฟลช 8 MB บนบอร์ดเอง

**ทุกอย่างทำงานอยู่ใน FPGA**: ไม่มี CPU, ไม่มีไมโครคอนโทรลเลอร์ และไม่มีโปรแกรมใดๆ รันอยู่
กติกาเกม ภาพ เสียง การสื่อสาร และเครื่องเล่นวิดีโอ เป็นวงจรดิจิทัลที่เขียนด้วยภาษา VHDL ทั้งหมด
(คอมพิวเตอร์ใช้เพียงตอนสร้างไฟล์และโหลดลงบอร์ดเท่านั้น)

![ภาพหน้าจอเกม (จากการจำลองวงจรทั้งหมด): โหมด CHAOS เปิดอยู่ ภารกิจ "SET IN BINARY" อยู่ด้านขวา แถบ RIVAL ด้านซ้ายคือความสูงกองของคู่แข่ง แถบแดงข้างกระดานคือขยะ 3 แถวที่รอเข้ามา](../figures/screenshot_chaos_on.png)

### 1.3 วิธีอ่านเอกสารนี้

เอกสารนี้เขียนให้ **คนที่ไม่เคยใช้ FPGA มาก่อน อ่านแล้วเข้าใจและสร้างชิ้นงานนี้ซ้ำได้เอง** จึงเริ่มจากพื้นฐาน
แล้วค่อยๆ ลงรายละเอียด:

* **บทที่ 2 พื้นฐานที่ต้องรู้**: FPGA คืออะไร, วงจรดิจิทัลที่ใช้, ภาษา VHDL, เครื่องมือ, บอร์ด และหลักการทุกเรื่องที่ใช้ในงาน
* **บทที่ 3 การหาข้อมูล**: เลือกหัวข้ออย่างไร และข้อจำกัดที่กำหนดการออกแบบ
* **บทที่ 4 การออกแบบแบบ Top-Down**: จากระบบทั้งหมด → วงจรในหนึ่งบอร์ด → การต่อสายระหว่างโมดูล → **ทุกโมดูลทีละตัว**
  พร้อมโค้ดจริงที่อธิบายทีละส่วน และ schematic ที่ Vivado สร้างจากโค้ด
* **บทที่ 5 การพัฒนา** และ **บทที่ 6 การทดสอบ**: ทำอะไรตามลำดับไหน พบปัญหาอะไร แก้อย่างไร ทดสอบอย่างไร
* **บทที่ 7 วิธีสร้างชิ้นงานซ้ำทีละขั้น**: ตั้งแต่ติดตั้งโปรแกรมจนเล่นได้บนบอร์ดสองบอร์ด
* **บทที่ 8-9**: วิธีเล่น และสรุปผล ตามด้วยเอกสารอ้างอิง
* **ภาคผนวก ก** รายชื่อไฟล์, **ภาคผนวก ข** schematic จาก Vivado ของทุกโมดูล

**โค้ดในเอกสาร**: กล่องสีเทาคือโค้ดจริงที่ดึงมาจากไฟล์โดยอัตโนมัติ เลขด้านซ้ายคือเลขบรรทัดในไฟล์นั้น
ซึ่งตรงกับเลขบรรทัดในไฟล์จริง อ่านโค้ดเต็มได้ที่ https://github.com/anakom-suvonvorn/FPGA-Tetris (branch `media` คือฉบับสมบูรณ์)
หรือในสื่อบันทึกข้อมูล โฟลเดอร์ `Source_Code`
คำอธิบายในโค้ด (comment หลัง `--`) เป็นภาษาอังกฤษ ส่วนคำอธิบายในเอกสารเป็นภาษาไทย

## 2. พื้นฐานที่ต้องรู้

### 2.1 FPGA คืออะไร

คอมพิวเตอร์ทั่วไป (และไมโครคอนโทรลเลอร์ เช่น Arduino) มี CPU ที่ **ทำคำสั่งทีละคำสั่ง** ตามโปรแกรม
ส่วน **FPGA (Field-Programmable Gate Array)** ไม่มี CPU และไม่ทำคำสั่ง แต่เป็นชิปที่มี "ชิ้นส่วนวงจร" เปล่าๆ จำนวนมาก
และสายไฟที่เลือกต่อได้ เมื่อโหลดไฟล์ตั้งค่า (เรียกว่า **bitstream**, ไฟล์ `.bit`) ลงไป ชิ้นส่วนเหล่านั้นจะถูกต่อกันเป็น
**วงจรดิจิทัลตามที่เราออกแบบ** ทุกส่วนของวงจรทำงานพร้อมกันตลอดเวลา เหมือนสร้างชิปขึ้นมาใหม่เอง

ชิ้นส่วนหลักในชิป XC7S15 ที่ใช้:

| ชิ้นส่วน | คืออะไร | มีกี่ตัว | ในงานนี้ใช้ทำอะไร |
|---|---|---|---|
| LUT (Look-Up Table) | ตารางความจริงขนาดเล็ก 6 อินพุต 1 เอาต์พุต: ทำวงจร AND/OR/XOR/บวก/เปรียบเทียบ ได้ทุกแบบ | 8,000 | วงจรตรรกะทั้งหมด |
| Flip-flop (FF) | หน่วยความจำ 1 บิต เปลี่ยนค่าเฉพาะตอนขอบขาขึ้นของนาฬิกา | 16,000 | ตัวนับ, รีจิสเตอร์, กระดานเกม |
| Slice | กลุ่มของ 4 LUT + 8 FF | 2,000 | (หน่วยที่ Vivado ใช้วางวงจร) |
| Block RAM | หน่วยความจำขนาด 36 Kb (แบ่งเป็น 18 Kb ได้ 2 ก้อน) | 10 ก้อน (45 KB) | frame buffer วิดีโอ, sprite, เสียง |
| DSP48 | ตัวคูณ 25 × 18 บิตสำเร็จรูป | 20 | ตัวคูณใน chaos_task, chaos_fx (สุ่มช่วงเวลา) และ media_engine: ใช้ 3 ตัว |
| I/O pin | ขาของชิปที่ต่อกับอุปกรณ์บนบอร์ด | 100 | ปุ่ม, สวิตช์, จอ, สาย, แฟลช |

### 2.2 วงจรดิจิทัลที่ใช้ในงานนี้

**สัญญาณนาฬิกา (clock)**: บอร์ดมีออสซิลเลเตอร์ 50 MHz คือสัญญาณที่สลับ 0/1 วินาทีละ 50 ล้านรอบ
(หนึ่งรอบ = 20 ns) ทุก flip-flop ในงานนี้เปลี่ยนค่าพร้อมกันที่ **ขอบขาขึ้น** ของนาฬิกาตัวนี้ตัวเดียว
เรียกการออกแบบแบบนี้ว่า **synchronous design**

**วงจรสองแบบ**:

* **Combinational** (วงจรเชิงผสม): เอาต์พุตขึ้นกับอินพุต ณ ตอนนั้นเท่านั้น เช่น ตัวบวก, ตัวเปรียบเทียบ, mux
  สร้างจาก LUT ต้องคำนวณเสร็จภายใน 1 รอบนาฬิกา (20 ns) ไม่อย่างนั้นวงจรจะผิด
* **Sequential** (วงจรเชิงลำดับ): มีหน่วยความจำ (flip-flop) ค่าใหม่ = ฟังก์ชันของค่าเดิมและอินพุต
  เปลี่ยนทีละขั้นที่ขอบนาฬิกา เช่น ตัวนับ (counter), shift register, state machine

**ตัวนับ (counter)**: รีจิสเตอร์ที่บวก 1 ทุกรอบนาฬิกา ใช้วัดเวลาได้ทุกช่วง เช่น นับ 434 รอบ = 8.68 µs = เวลา 1 บิตของ UART
หรือนับ 840,000 รอบ = 16.8 ms = เวลา 1 เฟรมภาพ

**Enable pulse**: แทนที่จะสร้างนาฬิกาช้าลง (เช่นหารนาฬิกาด้วย flip-flop) งานนี้ใช้นาฬิกา 50 MHz ตัวเดียวทั้งหมด
แล้วสร้างสัญญาณ "enable" ที่เป็น 1 เพียง 1 รอบนาฬิกา เป็นจังหวะ เช่น `frame_tick` เป็น 1 หนึ่งรอบในทุกๆ 840,000 รอบ
วงจรที่ต้องทำงานเฟรมละครั้งจะทำงานเฉพาะรอบที่ `frame_tick = '1'` (เหตุผลอยู่ในข้อ 4.6)

**State machine (FSM)**: วงจรที่มีรีจิสเตอร์ "สถานะ" (state) หนึ่งตัว ในแต่ละรอบนาฬิกาดูสถานะปัจจุบันและอินพุต
แล้วตัดสินว่าจะทำอะไร และรอบหน้าจะไปสถานะไหน ใช้ทำงานที่ต้องทำ "ทีละขั้น" เช่น ส่ง UART ทีละบิต
หรือกติกาเตตริส (ลองหมุน → ลองเลื่อน → ลองตก → ...) งานนี้มี FSM หลายตัว ตัวใหญ่สุดคือ `tetris_core` 23 สถานะ

**Metastability และ synchronizer**: สัญญาณจากภายนอก (ปุ่ม, สวิตช์, สายจากอีกบอร์ด, ข้อมูลจากแฟลช) เปลี่ยนเมื่อไรก็ได้
ไม่ตรงกับนาฬิกาของเรา ถ้าเปลี่ยนพอดีตอนที่ flip-flop เก็บค่า flip-flop อาจค้างอยู่ "ครึ่งทาง" ชั่วขณะ (metastable)
วิธีแก้มาตรฐานคือ **ส่งผ่าน flip-flop 2 ตัวต่อกัน** ก่อนใช้งาน ตัวที่สองจะได้ค่าที่นิ่งแล้วเกือบแน่นอน

**LFSR (Linear Feedback Shift Register)**: shift register 16 บิตที่บิตใหม่ = XOR ของบางบิต
ให้ลำดับตัวเลขที่ดูสุ่ม (ซ้ำรอบทุก 65,535 ครั้ง) ใช้ LUT น้อยมาก งานนี้ใช้สุ่มบล็อก ภารกิจ ช่องว่างของขยะ ฯลฯ
และเพราะ LFSR เดินทุกรอบนาฬิกา แต่ถูกอ่านตอนผู้เล่นกดปุ่ม ลำดับจึงไม่ซ้ำกันในแต่ละเกม

### 2.3 ภาษา VHDL

**VHDL** เป็นภาษาบรรยายวงจร (Hardware Description Language): สิ่งที่เขียนไม่ใช่คำสั่งให้ CPU ทำทีละบรรทัด แต่เป็น **คำบรรยายวงจร**
ที่ Vivado แปลงเป็น LUT และ flip-flop แต่ละไฟล์คือ "กล่องวงจร" หนึ่งกล่อง (`entity` บอกขาเข้า/ออก, `architecture` บอกข้างใน)
และกล่องใหญ่วางกล่องย่อยแล้วต่อสายถึงกันด้วย `port map` แบบเดียวกับการต่อวงจรบนกระดาษ

**จุดที่ต่างจากการเขียนโปรแกรม**: ทุกส่วนของโค้ดทำงาน **ขนานกันตลอดเวลา** และค่าใน `process` ที่ขึ้นกับ `rising_edge(clk)`
เปลี่ยนพร้อมกันทั้งหมดที่ขอบนาฬิกา ไม่ใช่ทีละบรรทัด

งานนี้ใช้ **VHDL-93** เท่านั้น (ไม่ใช้ของใหม่ใน VHDL-2008 เช่น `process(all)`) เพราะ FPGA Builder ของ TA
อ่านไฟล์เป็น VHDL-93 โค้ดจึงใช้ได้ทั้งกับ Vivado และ FPGA Builder

### 2.4 เครื่องมือ: จากโค้ดถึงบอร์ด

![ขั้นตอนตั้งแต่โค้ดถึงบอร์ด](../figures/fig_flow.png)

1. **เขียนโค้ด VHDL** (ไฟล์ `.vhd`) และไฟล์ **constraints** (`pins.xdc`) ที่บอกว่า port ไหนอยู่ขาไหนของชิป
2. **Simulation** (xsim ใน Vivado): รัน **testbench** ซึ่งเป็นไฟล์ VHDL ที่สร้างนาฬิกาและอินพุตปลอม แล้วตรวจเอาต์พุต
   เห็นสัญญาณทุกเส้นในทุกรอบนาฬิกา โดยยังไม่ต้องมีบอร์ด
3. **Synthesis**: Vivado แปลงโค้ดเป็นวงจรของ LUT, flip-flop, block RAM (ดูภาพ schematic ที่ Vivado สร้างได้ในบทที่ 4 และภาคผนวก ข)
4. **Implementation** (place & route): วางวงจรลงตำแหน่งจริงในชิปและเดินสาย แล้ว **ตรวจ timing**:
   ทุกเส้นทางจาก flip-flop ถึง flip-flop ต้องเร็วกว่า 20 ns ค่าที่เหลือเรียก **WNS (Worst Negative Slack)** ต้อง ≥ 0
5. **Bitstream**: สร้างไฟล์ `.bit`
6. **Program**: โหลด `.bit` ลงชิปผ่านสาย USB (JTAG) ด้วย openFPGALoader (ใน FPGA Builder ของ TA หรือสคริปต์ `program.bat`)

### 2.6 หลักการที่ใช้ (สรุปพร้อมตัวเลข)

**VGA 640 × 480**: จอวาดภาพทีละจุดจากซ้ายไปขวา ทีละบรรทัดจากบนลงล่าง วงจรไม่ได้ส่ง "ภาพ" แต่ส่ง **สีของจุดที่กำลังวาดอยู่ ณ ตอนนั้น**
ทางสาย R, G, B และพัลส์ HSYNC (จบบรรทัด) VSYNC (จบเฟรม) หนึ่งบรรทัดมี 800 ช่วงพิกเซล (มองเห็น 640 + ช่วงซ่อน 160)
หนึ่งเฟรมมี 525 บรรทัด (มองเห็น 480 + ซ่อน 45) พิกเซลละ 2 รอบนาฬิกา (25 MHz) จึงได้ 800 × 525 × 2 = **840,000 รอบต่อเฟรม**
= 50,000,000 / 840,000 = **59.52 เฟรมต่อวินาที**

**UART 8N1 115,200 bps**: สายว่างเป็น 1 → start bit 0 → 8 บิตข้อมูล (บิตต่ำก่อน) → stop bit 1 = 10 บิตต่อไบต์
บิตละ 50,000,000 / 115,200 = **434 รอบ** (8.68 µs) ไบต์ละ 87 µs ฝั่งรับไม่มีสายนาฬิกา จึงจับขอบลงของ start bit
แล้วรอครึ่งบิต (217 รอบ) เพื่ออ่านตรงกลางบิต จากนั้นอ่านทุก 434 รอบ

**SPI flash**: 4 สาย (CS_N, SCLK, MOSI, MISO) ส่งคำสั่ง READ `03h` + ที่อยู่ 24 บิต แล้วชิปส่งข้อมูลออกมาเรื่อยๆ
ทีละบิต (บิตสูงก่อน) ตราบที่ยังให้นาฬิกา ที่ SCLK 25 MHz ได้ 25 / 8 = **3.1 MB ต่อวินาที**

**IMA ADPCM**: เก็บเสียงเป็น "ผลต่าง" 4 บิตต่อตัวอย่าง แทน 16 บิต (เล็กลง 4 เท่า) ดูรายละเอียดในข้อ 4.7.16

**Sigma-delta**: ขา FPGA ออกได้แค่ 0 V หรือ 3.3 V แต่เสียงต้องมีหลายระดับ วิธีคือสลับขาเปิด/ปิดเร็วมาก (50 ล้านครั้งต่อวินาที)
ให้สัดส่วนเวลาที่เปิดเท่ากับระดับเสียง หูฟังตอบสนองไม่ทันจึงได้ยินเป็นค่าเฉลี่ย ดูข้อ 4.7.19

**การบีบอัดภาพ**: palette (เก็บเลขสีแทนสี), delta (เก็บเฉพาะจุดที่เปลี่ยนจากภาพก่อน), run-length (จุดสีเดียวกันติดกันเก็บเป็น "n จุด สี c")

**กติกาเตตริสสมัยใหม่** (Tetris Guideline): 7-bag randomizer, ghost piece, wall kick, lock delay 0.5 วินาที, ตารางขยะ

## 3. กระบวนการหาข้อมูล

### 3.1 การเลือกหัวข้อ

กลุ่มเริ่มจากรวบรวมไอเดียหลายแบบแล้วเปรียบเทียบ ตามเกณฑ์ของงาน (ใช้ FPGA อย่างน้อย 2 บอร์ด,
งานหลักต้องอยู่ใน FPGA, ยากกว่าแลป) และความชอบของกลุ่ม (อยากได้งานที่สนุก เล่นกับเพื่อนได้ และมีมุกมีม)

| ไอเดีย | ข้อดี | ข้อเสีย | ผล |
|---|---|---|---|
| อุปกรณ์ IoT / เครื่องใช้ | มีประโยชน์จริง | งานหลักมักอยู่ที่ไมโครคอนโทรลเลอร์, ไม่สนุก | ไม่เลือก |
| เครื่องเล่นวิดีโอ (Bad Apple) | ท้าทายเรื่องหน่วยความจำ | ใช้บอร์ดเดียว, ดูอย่างเดียว | นำไปเป็นส่วนหนึ่ง |
| เกมยิง 3D แบบ Doom | น่าทึ่ง | ใหญ่เกิน 8,000 LUT มาก | ไม่เลือก |

ข้อดีที่สำคัญที่สุดของเตตริสต่อสู้คือ **แบ่งเป็นชั้นได้**: ชั้นแรก (เกม + ต่อสู้) ทำเสร็จก็ส่งงานได้แล้ว
ชั้นต่อไป (CHAOS, สื่อจากแฟลช) เพิ่มทีละชั้นเมื่อมีเวลา ทำให้ความเสี่ยงต่ำแต่เพดานสูง

### 3.3 ข้อจำกัดที่กำหนดทิศทางการออกแบบ

1. **ไม่มี RAM ภายนอก** มีแค่ block RAM 45 KB ในชิป: ภาพ 640 × 480 เต็มจอ (12 บิต) ต้องใช้ 450 KB
   จึงเก็บภาพทั้งจอไม่ได้ → ภาพเกม **คำนวณสดทุกพิกเซล** (ไม่มี frame buffer) และวิดีโอลดเป็น 160 × 120
2. **LUT 8,000 ตัว**: ทุกฟีเจอร์ต้องคุ้ม เช่น ใช้ตัวตรวจการชนตัวเดียวร่วมกันทุกขั้น, ใช้ ROM ฟอนต์ตัวเดียวร่วมกันทุกบรรทัดข้อความ
3. **แฟลช 8 MB** อ่านได้ประมาณ 3.1 MB/วินาที: พอสำหรับวิดีโอที่บีบอัดแล้ว แต่ไม่พอสำหรับภาพดิบ
4. **ไม่มีวงจรเสียง (DAC)** ต่อกับช่องหูฟัง: ใช้ sigma-delta แทน
5. **VHDL-93**: FPGA Builder ของ TA อ่านเป็น VHDL-93 จึงใช้ไวยากรณ์ใหม่บางอย่างไม่ได้

## 4. การออกแบบ (Top-Down Design)

**Top-Down** คือเริ่มออกแบบจากภาพรวมก่อน แล้วแบ่งเป็นส่วนย่อยทีละระดับ จนแต่ละส่วนเล็กพอจะเขียนเป็นโมดูล VHDL
ที่ทำงานเดียวและทดสอบแยกได้ แต่ละระดับมองเป็น "กล่อง" ที่มีขาเข้าและขาออก แล้วเปิดกล่องดูว่าข้างในมีกล่องย่อยอะไรบ้าง
ต่อกันอย่างไร บทนี้เรียงตามระดับ:

* **ระดับ 0** ระบบทั้งหมด: บอร์ดสองบอร์ดและสายเชื่อม
* **ระดับ 1** วงจรในหนึ่งบอร์ด `top_tetris` มองเป็นกล่องเดียว: มีขาเข้า/ออกอะไรบ้าง
* **ระดับ 2** ข้างใน `top_tetris`: โมดูลย่อย 14 ตัวและสายที่ต่อระหว่างกัน
* **ระดับ 3** ข้างในแต่ละโมดูล และ **ระดับ 4** โมดูลย่อยชั้นล่างสุด (เช่น `debounce`, `uart_tx`)

### 4.1 ข้อกำหนดของระบบ (Requirements)

| รหัส | ข้อกำหนด |
|---|---|
| R1 | เล่นเตตริสได้ครบตามกติกาสมัยใหม่ บนจอ VGA ด้วยปุ่มบนบอร์ด |
| R2 | สองบอร์ดเล่นต่อสู้กันได้: ส่งขยะ, เห็นสถานะคู่แข่ง, เริ่มพร้อมกัน, ตัดสินผลตรงกัน |
| R3 | รู้ได้ว่าสายเชื่อมต่ออยู่หรือไม่ และเล่นคนเดียวได้เมื่อไม่มีคู่ |
| R4 | โหมด CHAOS: ภารกิจด้วยสวิตช์ → การโจมตีหรือโบนัส |
| R5 | เพลงและเสียงเอฟเฟกต์ระหว่างเล่น |
| R6 | วิดีโอพร้อมเสียงจากแฟลช: การโจมตี, ฉากชนะ/แพ้, sprite |

### 4.2 ระดับ 0: ระบบทั้งหมด

![ระดับ 0: บอร์ดสองบอร์ด เชื่อมด้วยสาย 3 เส้น แต่ละบอร์ดมีจอ หูฟัง และชิปแฟลช](../figures/fig_system.png)

ระบบประกอบด้วยบอร์ดสองบอร์ดที่ **โหลดวงจรเดียวกันทุกบิต** (ไฟล์ `top_tetris.bit` ไฟล์เดียว)
ไม่มีบอร์ดหลัก/บอร์ดรอง ทั้งสองบอร์ดเท่ากัน เหตุผล:

* ไม่ต้องสร้างและโหลดไฟล์สองแบบ ลดโอกาสผิดพลาด
* กติกาตัดสินถูกออกแบบให้ทั้งสองฝั่งคำนวณได้ผลเดียวกันเองโดยไม่ต้องถามกัน (ข้อ 4.7.6)

**สายเชื่อม**: ใช้สายจัมเปอร์ตัวเมีย-ตัวเมีย 3 เส้น **ต่อตรงจากขาถึงขา** ไม่มีอุปกรณ์อื่นคั่น
(ขาของทั้งสองบอร์ดเป็นสัญญาณ 3.3 V เหมือนกัน เอาต์พุตของบอร์ดหนึ่งจึงขับอินพุตของอีกบอร์ดได้โดยตรง):

| บอร์ด A | | บอร์ด B |
|---|---|---|
| J5 ขา 5 (L14, `link_tx`) | → | J5 ขา 6 (M13, `link_rx`) |
| J5 ขา 6 (M13, `link_rx`) | ← | J5 ขา 5 (L14, `link_tx`) |
| J5 ขา 2 (GND) | — | J5 ขา 2 (GND) |

สาย TX ของบอร์ดหนึ่งต้องไปที่ RX ของอีกบอร์ด (ไขว้กัน) ห้ามต่อ TX ชน TX และต้องต่อกราวด์ร่วมกัน
เพราะแรงดัน "0" กับ "1" วัดเทียบกับกราวด์ ถ้าไม่ต่อกราวด์ ฝั่งรับจะแยก 0 กับ 1 ไม่ออก

### 4.6 กฎการออกแบบที่ใช้ทุกไฟล์

1. **นาฬิกาเดียว (50 MHz)**: สิ่งที่ช้ากว่าใช้ "enable pulse" ยาว 1 รอบนาฬิกา (เช่น `frame_tick`) แทนการหารนาฬิกา
   เหตุผล: นาฬิกาที่หารเองทำให้ Vivado วิเคราะห์ timing ไม่ได้ และข้ามโดเมนนาฬิกายาก
2. **ทุกอินพุตจากภายนอกผ่าน flip-flop 2 ตัว** (synchronizer) ก่อนใช้ เพื่อกัน metastability
   (ปุ่ม, สวิตช์, สาย RX, ขาข้อมูลจากแฟลช)
3. **ไม่มี reset แยก**: ทุกรีจิสเตอร์มีค่าเริ่มต้นใน `signal ... := ...` ซึ่ง FPGA โหลดให้ตอนเปิดเครื่อง
4. **VHDL-93 เท่านั้น** เพื่อให้ใช้กับ FPGA Builder ของ TA ได้
5. **ทุกไฟล์ขึ้นต้นด้วยคำอธิบาย** ว่าโมดูลทำอะไร ทำอย่างไร และใช้เวลากี่รอบนาฬิกา

#### 4.7.1 `vga_sync`: ตำแหน่งพิกเซลและจังหวะเฟรม

**หน้าที่**: บอกทุกโมดูลว่า "ตอนนี้จอกำลังวาดพิกเซลไหน" (x, y) และสร้างพัลส์ HSYNC, VSYNC ให้จอ

| port | ทิศ | ความหมาย |
|---|---|---|
| `clk` | in | 50 MHz |
| `x` (0-799), `y` (0-524) | out | ตำแหน่งปัจจุบัน (รวมช่วงซ่อน) |
| `video_on` | out | 1 เมื่อ x < 640 และ y < 480 (นอกนั้นต้องส่งสีดำ) |
| `hsync`, `vsync` | out | พัลส์ sync (active-low) |
| `frame_tick` | out | 1 หนึ่งรอบนาฬิกาต่อเฟรม ตอนวาดส่วนที่มองเห็นเสร็จ |

1. `half` สลับ 0/1 ทุกรอบนาฬิกา ตัวนับเดินเฉพาะรอบที่ `half = '1'` จึงได้อัตรา 25 MHz โดยไม่ต้องสร้างนาฬิกาใหม่

4. `frame_tick` เป็น 1 เมื่อบรรทัดที่ 479 (บรรทัดสุดท้ายที่มองเห็น) จบ ซึ่งเป็นต้นช่วงซ่อนแนวตั้ง

#### 4.7.2 `debounce` และ `tetris_input`: ปุ่มกด → คำสั่ง

**ปัญหาของปุ่มจริง 3 อย่าง** และวิธีแก้ใน `debounce`:

1. ปุ่มเปลี่ยนเมื่อไรก็ได้ ไม่ตรงกับนาฬิกา → ผ่าน flip-flop 2 ตัว (`sync1`, `sync2`)
2. หน้าสัมผัสโลหะเด้ง (bounce) เปิดปิดรัวๆ หลายมิลลิวินาที → ยอมรับค่าใหม่เมื่อค่าคงที่ต่อเนื่อง `STABLE_CYCLES` รอบ
   (top ตั้งไว้ 250,000 รอบ = 5 ms)
3. ต้องการ "กด 1 ครั้ง = 1 คำสั่ง" → `pressed` เป็น 1 หนึ่งรอบนาฬิกาเมื่อค่าที่กรองแล้วเปลี่ยนจาก 0 เป็น 1

| ตกช้า | ทำทันที | ทำซ้ำทุก 2 เฟรม |

#### 4.7.3 `switch_filter`: กรองสวิตช์เลื่อน

**ปัญหาที่พบจากการทดสอบ**: สวิตช์เลื่อนบนบอร์ดเด้งรุนแรงกว่าปุ่ม และถ้าโยกค้างครึ่งทาง ขาจะลอย (ไม่ได้ต่อทั้ง 0 และ 1) อ่านค่ามั่วได้
ภารกิจ FLIP ("โยกสวิตช์ 10 ครั้ง") จึงนับผิด

**วิธีแก้ 2 ชั้น**:

1. ใน `pins.xdc` ตั้ง `PULLDOWN true` ทุกขาสวิตช์: ขาที่ลอยจะถูกดึงลงเป็น 0 อย่างนิ่ง
2. วงจร **integrator** ต่อสวิตช์: ทุก 1 ms (`TICK_CYCLES` = 50,000) สุ่มอ่านสวิตช์ ตัวนับ 0..10 **นับขึ้นถ้าอ่านได้ 1 นับลงถ้าได้ 0**
   เอาต์พุตเปลี่ยนเป็น 1 เมื่อตัวนับถึง 10 และเป็น 0 เมื่อถึง 0 การเด้งสั้นๆ แค่ทำให้ตัวนับขยับขึ้นลงนิดหน่อย
   ค่าใหม่ผ่านไปได้หลังอ่านค่าเดิมต่อเนื่องประมาณ 10 ms ซึ่งคนไม่รู้สึก

#### 4.7.5 `uart_tx` และ `uart_rx`: ส่ง/รับทีละบิต

**`uart_tx`**: เมื่อได้ `start` เก็บ 10 บิตลงรีจิสเตอร์ `frame = stop & data & start` แล้วส่ง `frame(0)` ออกขา
ทุก 434 รอบนาฬิกาเลื่อน `frame` ไปทางขวา 1 บิต ครบ 10 บิตก็หยุด `busy` เป็น 1 ตลอดการส่ง (87 µs)

<!-- CODE: src/common/uart_tx.vhd | ^begin | busy <= sending -->

**`uart_rx`**: FSM 4 สถานะ

1. **S_IDLE**: รอสายตกเป็น 0 (start bit เริ่ม)
2. **S_START**: รอครึ่งบิต (217 รอบ) ถึงกลาง start bit ถ้ายังเป็น 0 จริงก็ไปต่อ (ถ้าไม่ใช่ = สัญญาณรบกวน กลับ S_IDLE)
3. **S_DATA**: รอทีละ 434 รอบ 8 ครั้ง แต่ละครั้งตรงกลางบิตข้อมูลพอดี เลื่อนบิตเข้าจากด้านซ้ายของ `shreg`
   (บิตต่ำมาก่อน หลัง 8 บิตจึงเรียงถูกที่)
4. **S_STOP**: รออีก 1 บิต ถ้าเป็น 1 (stop bit ถูกต้อง) ส่งไบต์ออกพร้อม `valid = '1'` 1 รอบ ถ้าไม่ใช่ทิ้งไบต์นั้น

#### 4.7.6 `versus_link`: โปรโตคอลระหว่างบอร์ด

![รูปแบบข้อความ 1 ไบต์ สัญญาณบนสาย และกติกาการตัดสิน](../figures/fig_link.png)

**ทำไมใช้ข้อความ 1 ไบต์**: ข้อมูลที่ต้องส่งมีน้อยมาก (จำนวนแถว ≤ 31, ความสูง ≤ 20, หมายเลขการโจมตี ≤ 10)
แบ่งเป็นชนิด 3 บิต + ค่า 5 บิตก็พอ ไม่ต้องมีการต่อข้อความหลายไบต์ ไม่มีปัญหา "ข้อความขาดครึ่ง"
และ 1 ไบต์ส่งเสร็จใน 87 µs เร็วกว่าหนึ่งเฟรมภาพ (16,800 µs) มาก

| ชนิด (บิต 7-5) | ชื่อ | ค่า (บิต 4-0) | ส่งเมื่อ |
|---|---|---|---|
| 000 | HEARTBEAT | ความสูงกองบล็อกของฉัน 0-20 | ทุก 6 เฟรม (10 ครั้งต่อวินาที) |
| 001 | GARBAGE | จำนวนแถวขยะ 1-31 | ล้าง 2-4 แถวพร้อมกัน |
| 010 | LOST | - | ฉันแพ้ (ล้นจอ) |
| 011 | START | - | ฉันกดเริ่มเกม |
| 100 | ATTACK | หมายเลขการโจมตี 0-10 | ทำภารกิจสำเร็จและสุ่มได้การโจมตี |

**ฝั่งส่ง**: คำขอส่ง (`send_*`) อาจมาพร้อมกันหลายอย่าง จึงจำไว้ในรีจิสเตอร์ `*_p` แล้วส่งทีละไบต์เมื่อ `uart_tx` ว่าง
ตามลำดับความสำคัญ **START > LOST > ATTACK > GARBAGE > HEARTBEAT** ขยะที่รอส่งรวมกันได้ (2 + 4 = ส่ง "6" ครั้งเดียว)

**ฝั่งรับ**: ทุกไบต์ที่รับได้ ดูบิต 7-5 แล้วสร้างพัลส์ `got_*` 1 รอบนาฬิกา และตั้งตัวนับ `silence = 0`
ทุกเฟรมที่ไม่มีไบต์มา `silence` เพิ่ม 1 **`link_ok = 1` เมื่อ `silence` < 30** (มีไบต์มาภายใน 0.5 วินาทีล่าสุด)
HEARTBEAT ทำให้มีไบต์มาเสมอ ถ้าถอดสาย `link_ok` จะตกภายในครึ่งวินาทีและเกมเล่นแบบคนเดียว
ความสูงใน HEARTBEAT ยังใช้วาดแถบ RIVAL บนจออีกฝั่งด้วย (ได้สองอย่างในข้อความเดียว)

**การตัดสินผลโดยไม่มีบอร์ดหลัก** (เขียนใน `tetris_core` ข้อ 4.7.7):

* ใครแพ้ก็ส่ง LOST ทันที
* ได้รับ LOST ขณะที่ตัวเองยังเล่นอยู่ → **ชนะ**
* ได้รับ LOST ภายใน 6 เฟรมหลังจากที่ตัวเองเพิ่งแพ้ → **เสมอ** (ทั้งสองฝั่งแพ้เกือบพร้อมกัน ข้อความสวนกันบนสาย)

#### 4.7.7 `tetris_core`: กติกาเกม

นี่คือโมดูลที่ใหญ่ที่สุด (2,882 LUT, 1,048 flip-flop) เป็น **state machine ตัวเดียว 23 สถานะ**

**สิ่งที่เก็บไว้**:

| สัญญาณ | ขนาด | ความหมาย |
|---|---|---|
| `occ_r` | 20 แถว × 10 บิต | ช่องไหนมีบล็อก (1 = มี) |

#### 4.7.13 รูปแบบไฟล์สื่อ "TDM2" (ออกแบบเอง)

![แผนที่หน่วยความจำแฟลช: ข้างในไฟล์สื่อเรียงตามที่เก็บจริงพร้อมที่อยู่ sprite block อยู่ท้ายสุด](../figures/fig_flash.png)

ไฟล์ `media/game_media.bin` สร้างด้วย `tools/make_game_media.py` จากรายการใน `tools/media_plan.py`
และเขียนลงแฟลชที่ที่อยู่ **0x100000** (1 MB แรกเว้นไว้ให้ไฟล์ .bit) ทุกตัวเลขเก็บแบบ little-endian (ไบต์ต่ำก่อน)

**ลำดับในไฟล์ (ตามที่อยู่จริง)**:

| ที่อยู่ในแฟลช | ส่วน | ขนาด |
|---|---|---|
| 0x100000 | header: "TDM2", เวอร์ชัน, จำนวนรายการ (17), รายการแรก/จำนวนของแต่ละกลุ่ม (เพลง 0-1, โจมตี 2-4, แพ้ 5-12, ชนะ 13-16), ที่อยู่ sprite block | 16 ไบต์ |
| 0x100010 | directory: 16 ไบต์ต่อรายการ (bpp, ความเร็ว, โหมด, จำนวน record, ไบต์เสียงต่อ record, ที่อยู่ palette, ที่อยู่ record 0, ระดับเติม) | 17 × 16 ไบต์ |
| 0x100200 - 0x2BB1FF | รายการ 0-1: เพลง 2 เพลง (เสียงอย่างเดียว) | 1.73 MB |
| 0x2BB200 - 0x5DF2FF | รายการ 2-4: วิดีโอโจมตี Bad Apple!!, OIIA OIIA, Jevil | 3.14 MB |
| 0x5DF300 - 0x6E6BFF | รายการ 5-12: คลิป/รูปตอนแพ้ (rickroll, jump scare 2 แบบ, รูป 5 แบบ) | 1.03 MB |
| 0x6E6C00 - 0x7881FF | รายการ 13-16: คลิป/รูปตอนชนะ | 0.63 MB |
| **0x788200 - 0x78B97F** | **sprite block (อยู่ท้ายสุด)**: palette 256 สี (0x788200), Jevil 8 ท่า (0x788400), หน้าเพื่อน 4 รูป (0x78A980) | 14,208 ไบต์ |

แต่ละรายการเก็บเป็น **palette → records → ภาพ** และเริ่มที่ที่อยู่ที่หาร 256 ลงตัว

* **record** = ข้อมูล 1 ช่วงเวลา (วิดีโอ 10 ภาพต่อวินาที = 0.1 วินาที): header 8 ไบต์ (ที่อยู่ภาพ 3, ความยาวภาพ 2,
  ADPCM pred 2, idx 1) + เสียง 800 ไบต์ (1,600 ตัวอย่าง × 4 บิต) record ที่ r อยู่ที่ record0 + r × (8 + ไบต์เสียง)
  จึงกระโดดไปเล่นต่อกลางรายการได้ทันที (ใช้ตอนเพลงเล่นต่อหลังโดนโจมตี)
* **ภาพ** เก็บแยกจาก record และใช้ซ้ำได้ (เช่น ฉากหลัง Jevil 34 ภาพวนซ้ำ แต่เสียงยาว 40 วินาที)
* ภาพเก็บแบบ **palette + delta + run-length**: ภาพแรกเก็บทั้งภาพ ภาพต่อไปเก็บเฉพาะพิกเซลที่เปลี่ยน ด้วยไบต์ควบคุม 3 แบบ:
  `00nnnnnn` = SKIP ข้าม n+1 พิกเซล (frame buffer ยังมีภาพก่อนหน้าอยู่ จึงไม่ต้องทำอะไร),
  `01nnnnnn c` = FILL เติม n+1 พิกเซลด้วยสี c, `1nnnnnnn ...` = COPY n+1 พิกเซลตามมา (1/2/4/8 บิตต่อพิกเซลตาม palette)

#### 4.7.14 `spi_flash` และ `STARTUPE2`: อ่านแฟลช

**ขานาฬิกาของแฟลชเป็นขาพิเศษ**: ชิปแฟลชตัวเดียวกันนี้ FPGA ใช้โหลดตัวเองตอนเปิดเครื่อง ขานาฬิกาของมัน (CCLK)
จึงไม่ใช่ขา I/O ธรรมดา หลังโหลดเสร็จ วงจรของผู้ใช้เข้าถึงขานี้ได้ทางเดียวคือ primitive **STARTUPE2** ของ Xilinx:
สัญญาณที่ต่อเข้า `USRCCLKO` จะออกที่ขา CCLK (จึงไม่มีขานี้ในไฟล์ xdc) STARTUPE2 ไม่สนใจขอบนาฬิกา 3 ขอบแรก
`spi_flash` จึงส่งนาฬิกาเปล่า 8 ครั้งก่อนเริ่มใช้งาน (สถานะ S_WAKE)

**การอ่าน**: CS_N = 0 → ส่ง `03h` + ที่อยู่ 24 บิตทาง MOSI (บิตสูงก่อน, เปลี่ยนบิตตอน SCLK ขาลง ชิปอ่านตอนขาขึ้น)
→ อ่าน MISO ทีละบิต ครบ 8 บิตส่งไบต์ออก (`dout_valid`) ชิปเพิ่มที่อยู่เองจึงอ่านต่อเนื่องได้ → ครบตามจำนวนแล้ว CS_N = 1

#### 4.7.16 `adpcm_dec`: ถอดรหัสเสียง IMA ADPCM

**ทำไม ADPCM**: เสียง 16 บิต 16,000 ตัวอย่างต่อวินาที = 32 KB ต่อวินาที แฟลชมีที่ 7 MB สำหรับทุกอย่าง
ADPCM เก็บแค่ "การขยับ" 4 บิตต่อตัวอย่าง (8 KB ต่อวินาที เล็กลง 4 เท่า) เสียงยังใกล้ต้นฉบับ

**วิธีถอด**: เก็บค่าเสียงที่ทายไว้ `pred` (16 บิต) และขนาดก้าว `step` (จากตาราง 89 ค่า เลือกด้วย `idx`)
รหัส 4 บิตแต่ละตัวบอกว่าจะขยับ `pred` เท่าไร:

* บิต 3 = ทิศ (1 = ลง)
* ระยะ = step/8 + (บิต 2 ? step) + (บิต 1 ? step/2) + (บิต 0 ? step/4)
* แล้วปรับก้าว: รหัส 4-7 (ขยับมาก) → `idx` + 2/4/6/8 ก้าวโตขึ้น, รหัส 0-3 (ขยับน้อย) → `idx` − 1 ก้าวเล็กลง
  เสียงดังเปลี่ยนเร็วจึงได้ก้าวใหญ่ เสียงเบาได้ก้าวละเอียด

ตัวเข้ารหัสใน `make_game_media.py` ใช้สูตรเดียวกันทุกบิต ทั้งสองฝั่งจึงได้ `pred` และ `idx` เท่ากันเสมอ
วงจรแบ่งเป็น 3 ขั้น (3 รอบนาฬิกา) เพื่อให้แต่ละรอบสั้นพอสำหรับ 50 MHz ตาราง step อยู่ใน block RAM ครึ่งก้อน (RAMB18 1 ตัว)

#### 4.7.17 `media_ctrl`: เลือกว่าจะเล่นอะไร

state machine 4 สถานะ: **C_IDLE** (ไม่เล่น), **C_MUSIC** (เพลง), **C_ATTACK** (วิดีโอโจมตี), **C_END** (คลิปแพ้/ชนะ)

| เหตุการณ์ | สิ่งที่ทำ |
|---|---|
| เกมเริ่ม (`playing` 0 → 1) | เล่นเพลง (สลับ 2 เพลงทีละเพลง) → C_MUSIC |
| โดนโจมตีวิดีโอ (`media_hit`) | จำตำแหน่งเพลง = record ถัดไป − 2 แล้วเล่นวิดีโอ → C_ATTACK (Jevil: เปิด sprite ลอย) |
| วิดีโอโจมตีจบ | เล่นเพลงเดิม **ต่อจากจุดที่จำไว้** → C_MUSIC |
| เกมจบ (`result` ≠ 0) | ชนะ: สุ่ม 1 ใน 4 รายการชนะ, แพ้ (หรือจบเกมคนเดียว): สุ่ม 1 ใน 8 รายการแพ้, เสมอ: ไม่เล่น → C_END |

**ทำไมถอยหลัง 2 record**: ตอนโดนโจมตี เสียง 2 record สุดท้ายที่โหลดแล้วยังรออยู่ใน ring และจะถูกทิ้ง
จึงเริ่มใหม่ก่อนหน้านั้น 2 record (ได้ยินซ้ำนิดหน่อยดีกว่าขาดหาย) สถานะ ADPCM ที่ต้นของทุก record อยู่ใน header ของ record
เสียงจึงต่อได้ถูกต้อง

#### 4.7.18 `media_mix`: รวมภาพเกมกับสื่อ

ขั้นสุดท้ายของภาพก่อนออกขา VGA: สีเกมจาก `tetris_render` มาถึงหลัง (x, y) 2 รอบนาฬิกา ส่วนสีสื่อจาก `media_engine` มาถึงหลัง 3 รอบ

#### 4.7.19 `tetris_sound`: เสียงเอฟเฟกต์ + sigma-delta

**เสียงเอฟเฟกต์**: คลื่นสี่เหลี่ยม (chiptune) ความถี่ f สร้างจากตัวนับที่กลับบิตทุก 25,000,000 / f รอบนาฬิกา
แต่ละเอฟเฟกต์มีโน้ตไม่เกิน 4 ตัว (โน้ต, จำนวนเฟรม) เริ่มเมื่อมีเหตุการณ์: ล็อก, ล้างแถว, Tetris, ขยะเข้า, เริ่ม, ชนะ, แพ้,
ภารกิจเริ่ม/สำเร็จ/ล้มเหลว, ส่งการโจมตี, โดนโจมตี (เปิดด้วย SW5) บัซเซอร์เล่นเฉพาะเสียงเอฟเฟกต์

**ผสมเสียงลงขาเดียว (sigma-delta)**:

1. `loudness` (0-4,095) = ความดังที่ขาควรเป็นตอนนี้ = 1,536 (กึ่งกลาง) + เสียงจากสื่อ / 32 (−1,024..+1,023, ถ้าเปิด SW4)
   + 1,024 ขณะคลื่นสี่เหลี่ยมของเอฟเฟกต์เป็น 1
2. **"ถัง" (bucket) 12 บิต**: ทุกรอบนาฬิกาเท `loudness` ลงถังที่จุ 4,096 ทุกครั้งที่ล้น (บิตที่ 12 = 1) ขาออกเป็น 1 รอบนั้น
   และทิ้ง 4,096 ออก ใน 4,096 รอบถังล้นพอดี `loudness` ครั้ง ค่าเฉลี่ยของขา = loudness / 4,096
   สลับเร็ว 50 ล้านครั้งต่อวินาที หูฟังจึงได้ยินเป็นระดับเสียงต่อเนื่อง ไม่ต้องมีวงจร DAC

### 7.2 ติดตั้งโปรแกรม

1. **Vivado 2025.2** (ฟรี, รุ่น Standard) จาก AMD ติดตั้งที่ `D:\AMDDesignTools\2025.2` หรือใช้ Vivado ใน FPGA Builder ของ TA
   (สคริปต์หาทั้งสองที่)
2. **FPGA Builder ของ TA** (`D:\setup\FPGA_Builder_Package_V9`): มี openFPGALoader สำหรับโหลดบิตและเขียนแฟลช
3. **Python 3** + แพ็กเกจ: `python -m pip install numpy pillow pyserial`
4. **ffmpeg** (เฉพาะถ้าจะสร้างไฟล์สื่อใหม่จากวิดีโอต้นฉบับ)
5. คัดลอกโฟลเดอร์ซอร์สโค้ดไปไว้ในที่ที่ **ไม่มีช่องว่างหรือภาษาไทยในชื่อ path** (เช่น `D:\setup\assignment`)

### 7.3 สร้างไฟล์ .bit

```
cd D:\setup\assignment
tools\build.bat game
```

ใช้เวลาประมาณ 3-5 นาที เมื่อเสร็จจะพิมพ์ WNS (ต้องไม่ติดลบ) และได้ `game\build\top_tetris.bit`

ทางเลือก: ใช้ FPGA Builder ของ TA: ปิด Builder → `tools\load_into_builder.bat game` → เปิด Builder → กด Build แล้ว Program

### 7.4 สร้างและเขียนไฟล์สื่อลงแฟลช (ครั้งเดียวต่อบอร์ด)

1. ไฟล์ `media\game_media.bin` ที่สร้างเสร็จแล้วอยู่ในสื่อบันทึกข้อมูล (ถ้าจะสร้างใหม่: ใส่ไฟล์วิดีโอ/เพลง/รูปต้นฉบับตามรายการใน
   `tools\media_plan.py` ไว้ในโฟลเดอร์ `media\` แล้วรัน `python tools\make_game_media.py`)
2. ต่อบอร์ดกับคอมพิวเตอร์ ปิด FPGA Builder แล้วรัน:

```
tools\flash_media.bat media\game_media.bin
```

ใช้เวลาไม่กี่นาที ข้อมูลอยู่ในแฟลชถาวรแม้ปิดไฟ (ไม่ต้องทำซ้ำ) ทำกับทั้งสองบอร์ด
(ถ้าไม่ได้เขียนไฟล์สื่อ เกมยังเล่นได้ แค่ไม่มีเพลงและวิดีโอ)

```
tools\program.bat game
```

ทำกับทั้งสองบอร์ด (ไฟล์ `.bit` เดียวกัน) หรือใช้ปุ่ม Program ใน FPGA Builder
ถ้าต้องการให้บอร์ดจำเกมไว้แม้ปิดไฟ: `tools\program.bat game flash`

### 7.6 ต่อสายและเล่น

1. ต่อจอ VGA และหูฟังที่แต่ละบอร์ด
2. ต่อสายจัมเปอร์ 3 เส้นที่หัวต่อ J5 (ตรงจากขาถึงขา ไม่มีอะไรคั่น):
   บอร์ด A ขา 5 → บอร์ด B ขา 6, บอร์ด A ขา 6 → บอร์ด B ขา 5, ขา 2 ของทั้งสองบอร์ดต่อกัน (GND)
3. สวิตช์ SW7 ลง (ใช้สาย J5) SW4, SW5 ขึ้น (เพลง, เสียงเอฟเฟกต์) SW6 ขึ้นถ้าจะเล่นโหมด CHAOS (ทั้งสองบอร์ด)
4. ภายในครึ่งวินาทีทั้งสองจอขึ้น **LINKED**
5. กด **SW18** (ปุ่มกลาง) ที่บอร์ดไหนก็ได้ ทั้งสองบอร์ดเริ่มพร้อมกัน

### 7.7 ทดสอบด้วยบอร์ดเดียว (คอมพิวเตอร์เล่นเป็นคู่แข่ง)

1. SW7 ขึ้น (ใช้ USB แทนสาย J5) แล้วรัน `python tools\fake_opponent.py COM3` (COM ตามที่ Device Manager แสดง)
2. จอขึ้น LINKED พิมพ์ `s` = START, `g 3` = ขยะ 3 แถว, `l` = คู่แข่งแพ้, `x 8` / `x 9` / `x 10` = โจมตีด้วยวิดีโอ Bad Apple / OIIA / Jevil

### 7.8 แก้ปัญหา

| อาการ | สาเหตุที่เป็นไปได้ | วิธีแก้ |

| จอไม่ขึ้นภาพ | ยังไม่ได้โหลดบิต, สาย VGA หลวม | โหลดใหม่, เสียบสายแน่น |

7-segment แสดงจำนวนแถวที่ล้าง หรือวินาทีที่เหลือขณะมีภารกิจ

ในโหมด CHAOS ภารกิจโผล่ด้านขวาทุก 10-17 วินาที ทำด้วยสวิตช์ภารกิจให้ทันเวลา แล้วสุ่มได้การโจมตี (62.5 %) หรือโบนัส (37.5 %)

## 9. สรุปผล

### 9.1 ชิ้นงานที่เสร็จแล้ว

![ชิ้นงานจริง: บอร์ดสองบอร์ดต่อจอคนละจอ เชื่อมกันด้วยสาย 3 เส้น (สายบิดสีแดง-ดำ-น้ำตาลระหว่างบอร์ด) จอทั้งสองขึ้น LINKED และมีลำโพงสำหรับเสียงเกม จอซ้ายมีขยะที่คู่แข่งส่งมาอยู่ด้านล่างกระดาน](../figures/final_result.jpg)

เพื่อให้กดง่ายและรู้ทันทีว่าปุ่มไหนทำอะไร กลุ่มจึง **ออกแบบและพิมพ์ 3 มิติ ฝาครอบบอร์ดพร้อมปุ่มกด** ครอบทับบอร์ด EDGE ทั้งสองบอร์ด
ปุ่มพิมพ์ 3 มิติมีขนาดใหญ่กว่าปุ่มเล็กบนบอร์ด จึงกดได้สบายกว่ามากระหว่างเล่นเร็วๆ และบนฝาครอบมีป้ายบอกหน้าที่ของทุกส่วน:

* ปุ่ม **ROTATE / LEFT / RIGHT / HARD DROP / SOFT DROP**
* **LINES** เหนือ 7-segment (จำนวนแถวที่ล้าง หรือวินาทีที่เหลือของภารกิจ)
* **TASK SWITCHES** เหนือสวิตช์ภารกิจ 8 ตัวทางซ้าย
* สัญลักษณ์เหนือสวิตช์ตั้งค่าทางขวา: **PC** (เชื่อมกับคอมพิวเตอร์), **♦** (โหมด CHAOS), **ลำโพง** (เสียงเอฟเฟกต์), **โน้ตดนตรี** (เพลง), **II** (พักเกม)
* ช่องเปิดตรงขั้วต่อทุกจุด (USB, VGA, ช่องหูฟัง, J5) จึงต่อสายได้โดยไม่ต้องถอดฝาครอบ

![บอร์ดพร้อมฝาครอบและปุ่มที่พิมพ์ 3 มิติ: ป้ายชื่อปุ่ม, LINES เหนือ 7-segment, TASK SWITCHES และสัญลักษณ์ของสวิตช์ตั้งค่า สาย 3 เส้นของ J5 ต่ออยู่ที่ขอบขวา](../figures/just_board_with_3d_printed_on.jpg)

### 9.3 สิ่งที่ได้เรียนรู้

* การออกแบบแบบ Top-Down ทำให้แบ่งงานได้ชัด และเมื่อมีปัญหาก็ไล่หาได้ทีละระดับ
* simulation ที่ตรวจผลเองช่วยประหยัดเวลามาก เพราะการ build หนึ่งครั้งใช้หลายนาที
* ฮาร์ดแวร์จริงไม่ตรงกับเอกสารเสมอไป ต้องมีวงจรทดสอบเล็กๆ เพื่อยืนยัน
* ทรัพยากรของ FPGA มีจำกัดจริง ต้องเลือกโครงสร้างที่ประหยัด (ใช้วงจรร่วมกัน, ทำงานทีละขั้นแทนพร้อมกัน)

### 9.4 ข้อจำกัดและแนวทางพัฒนาต่อ

* ชิปเต็มแล้ว (slice 98 %, block RAM 100 %): ฟีเจอร์ใหม่ต้องลดของเดิมก่อน หรือใช้ชิปที่ใหญ่กว่า
* วิดีโอมีความละเอียดเพียง 160 × 120 เพราะไม่มี RAM ภายนอก
* แนวทางต่อไป: มินิเกมเพิ่ม, เล่นได้มากกว่า 2 คน (ต่อสายแบบวง), ใช้คีย์บอร์ด PS/2

## ภาคผนวก ข. schematic จาก Vivado ของทุกโมดูล

สร้างด้วย Vivado: Open Elaborated Design → Schematic แล้วเลือกแต่ละ instance → Export to PDF (หมุนภาพแล้ว)
ภาพในเอกสารย่อลงเพื่อให้พอดีหน้า ไฟล์ PNG ความละเอียดสูงและ PDF ต้นฉบับ (ซูมได้ไม่จำกัด) อยู่ในโฟลเดอร์ `vivado_schematics` ของสื่อบันทึกข้อมูล
และบน GitHub ที่ `submission/figures/` ชื่อไฟล์คือชื่อ instance ในโค้ด (`u_core` = `tetris_core` เป็นต้น) ภาพของโมดูลย่อยชั้นที่สองมีกรอบสีน้ำเงินของโมดูลแม่ล้อมอยู่
