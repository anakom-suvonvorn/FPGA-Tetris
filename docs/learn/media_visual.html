Tetris Duel Media Internals

How pictures, videos and sound get from a video file on your PC into the board's flash chip, and how the FPGA gets them back out and onto the screen and the speaker, 60 times a second. It starts from zero: no knowledge of memories, flash chips or video formats needed.

Companion to docs/learn/08_flash_walkthrough.md (test 06: media_player, file format "TDMF") and 09_media_walkthrough.md (the game: media_engine, format "TDM2"). Every diagram runs the same rules as the VHDL and the Python, and the byte values come from your real media/game_media.bin. The code itself is in the last part, Read the code with help, where clicking a short name like pb_v tells you what it means and shows every line that uses it.

start hereYour questions, and where each one is answered

The page is in the order things happen: first what memory is, then how the file is made and written, then how the FPGA reads it and what it does with every byte. If you only want one answer, jump straight to it:

the big pictureThe whole journey of one video, in one diagram

There are two separate trips. The top half happens on your PC, once, whenever the media changes: Python turns the video and music files into one file of bytes, and a tool writes that file into the flash chip on the board. The bottom half happens on the board, every time the game runs: our VHDL reads those bytes back out of the flash, a few thousand at a time, exactly when they are needed.

The flash chip is where the two trips meet. It keeps its contents when the power is off, so the top half only has to happen once. Click any box to see what it does.

from zeroWhat is a memory? RAM, ROM, flash, block RAM

Every memory, from a USB stick to the tiny ones inside the FPGA, is the same idea: a row of numbered boxes. Each box holds a fixed number of bits (the memory's width, for example 8 bits = one byte). The number of a box is its address. How many boxes there are is the memory's depth. To read, you give an address and get back what is in that box. To write, you give an address and a value, and the box takes the value.

RAM means "random access memory": you can read or write any box, in any order, equally fast. That's opposed to, say, a tape, where you have to wind past everything in between. ROM is "read-only memory": the boxes are filled when the chip (or the design) is made and never change, like the font of the game's text. Flash is a kind of memory that keeps its contents without power (a USB stick, the SSD in your laptop, the 8 MB chip on our board) but is slow and awkward to write.

Our design uses four kinds of storage, each for a different job:

The whole game media is 6.86 MB, and the FPGA can hold 45 KB. That gap is the reason for everything on this page: the media lives in the flash, and only the part needed right now (one picture, a fraction of a second of sound) is copied into block RAM.

Try a memory: 16 boxes of 8 bits, like every BRAM in the design

A block RAM in our design has a write side (address wa, data wd, write enable we) and a read side (address ra, answer q). Nothing happens between clock edges. At each rising edge of the clock: if we is 1 the box at wa takes wd, and q takes the value of the box at ra. So you see the answer for an address one clock after you gave it. If you read the box you are writing in the same edge, you get its old value. Every memory on this page works like this.

write: wawd 0x
read: ra
clock edges0
q (read answer)00
type mem_t is array (0 to 15) of std_logic_vector(7 downto 0);
signal mem : mem_t;
...
process(clk) begin
  if rising_edge(clk) then
    if we = '1' then mem(wa) <= wd; end if;
    q <= mem(ra);      -- 1 clock later
  end if;
end process;

That little process is, line for line, how the frame buffer, the palette, the sound ring, Jevil and the faces are written in media_engine.vhd (for example the frame buffer banks at L576–584). The next section shows how Vivado turns it into a block RAM.

BRAM · ram_style · banksBlock RAM, and how Vivado decides to use it

An FPGA chip is a big grid of small identical pieces: LUTs (tiny lookup tables that do the logic), flip-flops (1-bit memories, one per register bit) and wires between them. Between the columns of those, the chip maker added a few special blocks that would be wasteful to build out of LUTs: block RAMs (ready-made memories) and DSPs (ready-made multipliers). Our XC7S15 has 10 block RAM tiles. Each holds 36 Kbit (36,864 bits, about 4.5 KB) and can also be used as two independent halves of 18 Kbit. The diagram shows what our game keeps in each one, from the real build report (game/build/utilization_by_block.txt: 6 whole tiles + 8 halves = all 20 halves).

Vivado decides, from the way the code is written

The FPGA itself decides nothing: it is just switches set by the bitstream. Vivado (the synthesis step of build.bat) reads the VHDL, and when it sees an array signal used in a certain pattern it says "that's a memory" and picks how to build it. This is called inference. Nobody writes "use block RAM" in our code (except the ram_style hint, below); the pattern is the request. Try the questions Vivado asks:

Why the read must be inside the clocked process: a block RAM can only answer at a clock edge (that's how the silicon is built). If the code asks for the answer with no clock in between (q <= mem(ra); outside the process), Vivado can't use a block RAM, and builds the memory from LUTs instead (LUTs can answer instantly). That's why every memory in media_engine has its read inside if rising_edge(clk), and why its picture comes out a clock later.

ram_style: an attribute is a note to Vivado attached to a signal. attribute ram_style of pal, ring, faces : signal is "block"; (media_engine L121–122) means "build these as block RAM, don't guess". We needed it: once, Vivado guessed the block RAM was running out and built a Jevil bank from LUTs, which cost 512 LUTs.

Tile shapes: why the frame buffer is cut into 5 banks

A tile isn't one fixed shape. It can be wired as many narrow boxes or few wide ones, always about 36 Kbit: 32,768 × 1 bit, 16,384 × 2, 8,192 × 4, 4,096 × 9, 2,048 × 18, 1,024 × 36, or 512 × 72 (a half: 16,384 × 1 ... 512 × 36). A memory that doesn't fit one shape uses several tiles side by side (for width) and stacked (for depth). Enter a memory and see what it costs in each shape:

depth (boxes)width (bits)

So the 19,200-byte frame buffer is written as 5 separate memories of 4,096 bytes (g_fb, a for ... generate loop, media_engine L572–585). Each one fits a tile in the 4,096 × 9 shape exactly. The address of a pixel is split in two: which bank, and where in the bank. Because 4,096 = 212, that split costs nothing: the low 12 bits are the place, the bits above are the bank.

S25FL064L · addresses · eraseThe flash chip: 8 MB that survive a power cut

Next to the FPGA on the board sits an S25FL064L: a flash memory chip of 64 Mbit = 8 MB = 8,388,608 bytes. Like every memory it is a row of numbered boxes, here 8,388,608 boxes of 8 bits. The address of a box needs 24 bits (224 = 16,777,216 is the first power of 2 bigger than 8,388,608), so addresses go from 0x000000 to 0x7FFFFF.

Why hexadecimal? 0x means "hexadecimal": base 16, digits 0–9 then A–F. Each hex digit is exactly 4 bits, so a byte is always 2 hex digits and a 24-bit address 6. Round binary sizes become round hex numbers: 1 MB = 1,048,576 bytes = 0x100000. That's where our media file starts.

a number(decimal, or hex with 0x)

The chip holds two things. At address 0 the FPGA's own design (the "bitstream", about half a megabyte) if you ever used the Builder's "PROM" button: at power-up the FPGA reads it from there by itself. From 1 MB on, our media file. Move over the map:

The odd rule of flash: writing can only turn 1s into 0s

Reading flash is easy and fast. Writing is not. An empty (erased) flash box reads 0xFF: all 8 bits are 1. Programming a byte can only change 1s into 0s. The only way to get 1s back is an erase, and an erase can't do single bytes: it clears a whole sector of 4 KB (4,096 bytes) or a block of 64 KB back to FF. So writing a file means: erase every sector it will touch, then program it in pages of 256 bytes. Try it on 8 bytes of a sector:

program bytewith 0x

This is also why our testbenches without a flash in them see FF everywhere (the flash_miso port of top_tetris defaults to '1'): they find no "TDM2" and play no media, exactly like a board with an empty flash.

flash_media.bat · openFPGALoader · spiOverJtagHow the bytes get into the flash chip

Your PC is connected to the board by one USB cable, and that cable doesn't go to the flash chip. It goes to an FT2232 chip on the board, which turns USB into two things: a serial port (the UART we use for the versus link test) and JTAG, the 4-wire connection used to load designs into the FPGA. The flash chip is only wired to the FPGA. So to write the flash, the PC has to go through the FPGA, and the FPGA has to be running a design that passes the data on. spi_flash.vhd · STARTUPE2Reading it back: SPI, one clock at a time

From now on everything happens on the board. Our spi_flash block talks to the flash chip over four wires with SPI (Serial Peripheral Interface): CS_N low means "chip, I'm talking to you"; SCLK is a clock that we make, one bit moves per SCLK period; MOSI carries our bits to the chip; MISO brings the chip's bits back. The chip reads MOSI when SCLK rises and puts its next MISO bit out just after SCLK falls. A read is always: CS_N low, the command byte 03, 24 address bits, then as many data bytes as we keep clocking for (the chip counts the address up by itself). CS_N high ends it.

The SCLK pin is special: STARTUPE2

CS_N, MOSI and MISO go to ordinary FPGA pins (game/pins.xdc: C11, B11, B12). The flash's clock pin, however, is wired to the FPGA's CCLK: the pin the FPGA itself uses to read its bitstream from this very flash at power-up. It isn't connected to the normal logic. The only way in is a built-in block called STARTUPE2: whatever we connect to its USRCCLKO input comes out on CCLK (top_tetris L365–376). That's why spi_flash has an sclk output that goes to the top level instead of to a pin, and why after power-up it first sends 8 dummy clocks (state S_WAKE): the first 3 edges are swallowed while CCLK switches over to us.

This is spi_flash.vhd running in your browser, line for line, against a pretend flash chip holding the real first bytes of game_media.bin. Every column is one tick of the 50 MHz clock (20 ns). Watch ph count clocks inside each half of an SCLK period, sh_out push the command and address out of its top bit, sh_in collect bits from the right, and dout_valid flag each finished byte.

SCLK speed

The numbers. At full speed (half_period = 1) SCLK is low for one clock and high for one clock: 25 MHz, one bit every 2 clocks, one byte every 16 clocks = 3.125 MB a second. A read costs 32 bits = 64 clocks of command and address before the first byte, plus a few clocks at the end. The engine uses one read per thing it needs: 16 bytes of header, 8 bytes of a record header, a picture, a record's sound.

Why MISO is read at the end of the high half. Our SCLK goes out through STARTUPE2 and a board wire, the chip answers, and the answer comes back over another wire: several nanoseconds each way. A whole SCLK period is only 40 ns. So spi_flash takes the MISO bit at the very last moment, in the same clock edge that pulls SCLK low again (L144–146). The chip only changes MISO a few ns after it sees that falling edge, so the bit is still the old, stable one.
hold (added for the game, L56 and L138): while it is '1' at the start of a byte, the reader just doesn't start the next byte: SCLK stays low, and SPI chips don't mind a paused clock. media_engine holds while its picture decoder is still busy with the previous byte (see When does it all happen?). Choose "read with hold" above to see it.

S_ · M_ · E_ · D_ · C_ statesEvery state machine, state by state

A state machine is a process with a variable state that remembers "which step am I at". Every clock it runs only the code of its current state, which does that step's work and decides whether to move on (state <= …). The prefixes tell you which machine a state belongs to: S_ spi_flash, M_ media_player (test 06), E_ media_engine (the game), D_ its picture decoder (a second, smaller machine running beside it), C_ media_ctrl. The "_W" states mean "wait": the state before it started a flash read, the _W state takes the bytes as they arrive and leaves when the read is done.

media_engine · screen pipeline · paletteThe frame buffer: from (x, y) to a colour

  
A monitor isn't sent "pictures". It is sent the colour of one pixel at a time, left to right, top to bottom, 25 million pixels a second, while vga_sync counts where the beam is (x, y). Whatever we want to show has to be ready the moment the beam gets there. For the game that's easy: the colour is calculated from the field. A video frame can't be calculated, so it has to be stored somewhere the beam can look it up: the frame buffer. It's simply a memory with one box per picture pixel (160 × 120 = 19,200 boxes), each holding that pixel's palette number. The loader writes it once per new picture; the screen pipeline reads it 60 times a second.

Why 3 clocks? Each step is a register: an address in clock 1, the block RAM's answer in clock 2 (block RAM always answers one clock later, see What is a memory?), the palette (another block RAM) in clock 3. Splitting it like that keeps each clock's work short. The game's own picture (tetris_render) is ready after 2 clocks, so media_mix delays it by one, and HSYNC / VSYNC travel through the same registers, so everything stays lined up: the whole screen is drawn 4 pixel clocks "late", which nobody can see.

  
The same palette RAM, two readers. The palette block RAM has two ports. Port A writes colours while a palette loads, and otherwise reads the picture's colour (pa <= pal_wa when pal_we = '1' else '0' & fb_q, L616). Port B reads the sprite colour from entries 256..511 for Jevil and the faces (L630–633). While a palette loads, pic_ok is '0' so the picture isn't shown and nobody sees the wrong colours.







  
frame_tick · E_RH / E_PIC / E_SND · holdWhen does it all happen? One frame, clock by clock

  
One screen frame is 800 × 525 pixel steps, 2 clocks each: 840,000 clocks = 16.8 ms. The beam draws the 480 visible lines in 768,000 clocks (15.36 ms), then the screen is blank for 45 lines: 72,000 clocks = 1.44 ms. frame_tick is a one-clock pulse right at the start of that blank time. That's the moment the engine starts loading a record. The new picture must be written before the beam reaches each pixel of the next frame; if the beam overtakes the loader, the bottom of the screen still shows the old picture for one frame: tearing.

ring · wr_ptr · rd_ptr · fill · low waterThe sound ring: bursts in, a steady stream out

  
Sound has a hard rule: it must come out at exactly 16,000 samples a second, every 3,125 clocks, never early, never late, or you hear clicks and gaps. But the flash delivers sound in bursts: a whole record (800 bytes for a video, 1,024 for music) in a fraction of a millisecond, then nothing until the next record. Something has to sit in between and hold the bytes that have arrived but haven't been played yet. That's the ring: a 2,048-byte block RAM used as a queue.

  
Why "ring"? A memory can't move its contents along like a real queue. So instead the two positions move: wr_ptr = where the next byte from the flash goes, rd_ptr = the next byte to play. Each only ever counts up, and after box 2,047 it goes back to box 0 (if wr_ptr = RING_SIZE - 1 then wr_ptr <= 0), as if the boxes were arranged in a circle. fill = how many bytes are waiting. In the same clock a byte can come in (+1) and go out (−1), so both parts only set a variable dfill, and fill <= fill + dfill is written once at the end (L564–566).

Reading out (L546–563): a counter scnt counts to 3,125 (50 MHz / 16 kHz). Each time it wraps, one 4-bit code goes to the ADPCM decoder: first the low half of the byte at rd_ptr, next time the high half (hi_nib remembers which), and only then rd_ptr moves on and fill drops by 1. So the ring drains at 8,000 bytes a second. If fill is 0 when a code is due, nothing is sent: the decoder keeps its last sample (a short silence, no click).

adpcm_dec.vhd · adpcm_encode · STEPS · IDXADPCM, slowly: how 4 bits can carry a 16-bit sound

  
A sound sample is a 16-bit number (−32,768 … 32,767): how far the speaker is pushed at that moment. ADPCM stores only 4 bits per sample and still sounds almost the same. This section builds it up one idea at a time. These are the only names you need:

1. The idea: don't send the sample, send how far it moved, roughly

  
Sound changes smoothly: at 16,000 samples a second, each sample is close to the one before. So instead of the sample itself, ADPCM sends which way and roughly how far the sound moved since the last one. "Roughly" is the trick: there are only 8 possible distances (3 bits), plus up or down (1 bit). The decoder moves its guess pred by the chosen distance. The guess is never exactly right, but it stays close, and the next code corrects whatever error is left.

  
The 8 distances can't be fixed numbers: a whisper needs moves of 10, a loud drum moves of 5,000. So the distances are measured in a unit, step, and the step size itself changes with the sound. That's the A (adaptive) in ADPCM; the D (differential) is sending differences; PCM is plain sampled sound.

So what are the /8, /4, /2? Read bits 2..0 as a number in quarter steps: bit 2 is worth 1 step, bit 1 half a step, bit 0 a quarter step. That's ordinary binary, just with a "binary point": 101 = 1 + ¼ = 1¼ steps, the bottom of slot 5. Then + step/8 (an eighth = half a slot) moves the guess from the bottom of the slot to its middle. The middle is the best place: whatever the real sample was in that slot, the guess is at most ⅛ step away (except in the top slot, which has no upper end).

  
Why halves, quarters and eighths, and not thirds? Dividing by 2, 4 or 8 is free in hardware: it's just leaving off the lowest bits. step(14 downto 3) in adpcm_dec is step / 8 with no logic at all, only wires. A division by 3 would need a real divider. Note that the division rounds down: with step = 1,060, step / 8 is 132, not 132.5. The encoder rounds the same way, so it doesn't matter.

  
How the encoder finds the slot (adpcm_encode, make_game_media.py L94–103): it asks three yes/no questions, biggest first, like weighing on a balance. Is the difference at least 1 step? If yes, bit 2 = 1 and take a step off. Is what's left at least ½ step? Bit 1. At least ¼ step? Bit 0. Three questions, three bits: that's the slot. The sign goes in bit 3 first: if the sample is below pred, bit 3 = 1 and the encoder works with the distance downwards.


  
3. Why the step has to change size

  
With a fixed step there's always a bad case. The finest the guess can get is ⅛ step from the truth, and the furthest it can move in one sample is 1⅞ steps. A small step is precise but slow: on loud sound the real samples run away from the guess, which can't keep up (it sounds harsh and distorted). A big step keeps up with anything but is coarse: quiet sound gets a hiss of errors around it. So after every sample the step is adjusted using the code that was just sent, which both sides know:

  
    
    
  • the code said "less than 1 step" (bits 2..0 = 0 … 3): the step was bigger than needed → idx − 1: about 10 % smaller.
    • 
    
  • the code said "1 step or more" (4 … 7): the step was too small, the sound is getting away → idx + 2, + 4, + 6 or + 8: 21 %, 46 %, 77 % or 114 % bigger, the further out the more.
    • 
  

  
It grows fast and shrinks slowly, on purpose. A step that is too small makes the guess fall behind the sound, which you hear as distortion, so it must catch up within a few samples. A step that is too big only adds a little noise, so it can shrink gently. In steady sound the two balance out: some codes are big, some small, and idx hovers around the right size. Because the encoder and the decoder see the same codes, they make the same changes and their idx stays equal without ever being sent.


  
4. The 89 step sizes

  
STEPS is a list of 89 sizes from 7 to 32,767, each about 10 % bigger than the one before (the table grows by multiplying, not adding). Why multiplying? Because loudness works in ratios: going from 10 to 20 is as big a change to the ear as 10,000 to 20,000, so the sizes are spread evenly in ratio. Why 7 to 32,767? 7 is small enough for the quietest sounds (with step 7 the moves are 0, 1, 3, 4, 7, 8, 10 and 11), 32,767 is the whole 16-bit range. How many 10 % steps fit from 7 to 32,767? 1.188.6 ≈ 32,767 / 7, so 89 entries. The exact numbers are the standard IMA ADPCM table (Interactive Multimedia Association, 1992), the same one used in ADPCM .wav files and in many old games. records · pacing · rec_pos − 2Video with sound: how they stay together

  
A video item is cut into records, one per video frame. At 10 frames a second each record holds one picture (or a pointer to one) and 0.1 s of sound: 1,600 samples = 800 bytes. The two halves are tied together by one rule: the next record is loaded when the sound needs it (the ring falls below low water), and its picture goes on screen at that moment. Sound can't speed up or slow down, so the pictures follow the sound's clock, and they can't drift apart, however long the video is.

  
The picture of a record appears a little before its sound starts: the ring still holds the end of the previous record's sound (at most 264 bytes = 33 ms). 33 ms is less than one video frame, too little to notice.

  

    

    

    

  

  
How regular are the loads? (one record every 5 or 6 screen frames)

  
A screen frame is 840,000 clocks = 16.8 ms: 59.52 frames a second, a little under 60 because our pixel clock is 25 MHz instead of the standard 25.175 MHz. A 10 fps record holds exactly 0.1 s of sound (800 bytes), which lasts 0.1 / 0.0168 = 5.952 screen frames. At every frame tick the engine checks the ring afresh: "is it below low water now?" So most of the time the answer becomes yes after 6 frames, and about one time in 21 after 5. It can never be 4 or 7. The 0.048 frame that each record is "short" of 6 adds up, and when it reaches a whole frame, that one record is loaded a frame early and the count starts over. Nothing piles up, because every decision uses the real amount of sound left in the ring, not a frame counter.

  
For each picture this means it appears between about 16 and 33 ms before its own sound starts: always a little early, never late, never drifting. Play with it here (30 s of video, simulated with the real numbers). The lower chart is a sawtooth: with every record loaded 6 frames after the last, the picture comes a little less early each time (6 frames is slightly more than the 5.952 its sound lasts). When the lead would drop below one frame, the ring is already below low water one tick sooner, that record comes after 5 frames, and the lead jumps back up by a whole frame (16.8 ms).

Carrying on with the music after an attack

  
When a media attack hits, media_ctrl stops the music and plays the attack. Later the music should continue where it was. The engine tells it rec_pos: the next record it was going to load. But the ring already held up to 2 records that were loaded and not yet heard (music keeps the ring between half and completely full). So media_ctrl saves rec_pos − 2 (mus_save, L126) and later plays the music from there: you may hear up to a quarter second twice, but never miss any. Each music record starts with the decoder state stored in its header, so starting in the middle is exact.

media_player · lfsr8 · make_media.lfsr_bytesThe VERIFY block: checking 262,144 bytes without storing the answers

  
Test 06 had to answer one question before anything else: does our SPI reader get every byte right, at full speed? A picture with one wrong byte might look fine, so it needs a real check. The trick: fill 256 KB of the flash with a sequence that the FPGA can make by itself. Then while reading, it makes the same sequence and compares byte by byte. No need to store the right answers anywhere.

  
The sequence comes from an LFSR (linear feedback shift register), the same kind of random-number maker as the game's piece picker: a 16-bit register; each step shifts it left by one and the new bit 0 is bit 15 XOR bit 13 XOR bit 12 XOR bit 10. It starts at ACE1; each byte is its low 8 bits, then it steps 8 times. In VHDL the 8 steps are a for loop in a function (lfsr8, L201–208): it doesn't take 8 clocks, it becomes 8 layers of XOR gates that all settle within one clock.

  

    

    

    

    

  

  
Your result on the board (2026-10-20): VERIFY 0000 BAD, 0083 MS at 25 MHz. 262,144 bytes × 16 clocks = 4,194,304 clocks = 83.9 ms, and the millisecond counter only counts whole milliseconds. The game's engine has no verify block: the media file there is checked by Python before it is written (check_item) and by flash_media.bat check after.
