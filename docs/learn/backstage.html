Tetris Duel Backstage

Six things that happen out of sight: how all the on-screen text shares one font table, how we test circuits without a board, how Jevil floats around, what every Python and batch script on the PC does, how two boards agree on who won, and how a monitor finds the pixels with no clock wire. Every number here comes from the project's real files.

part 1 · src/game/text_multi.vhd

"One font ROM": how the text stopped eating the chip

What a ROM is inside an FPGA

A ROM (read-only memory) is a fixed table: give it an address, it gives back the value stored there. In our VHDL the font is a constant array in text_pkg.vhd: 64 characters, each a 5 × 7 picture, so 35 bits per character. Bit 5·row + column says whether that dot is lit.

An FPGA has no ROM chip for this. Vivado builds the table out of LUTs (the small logic blocks, 8,000 of them in our XC7S15). Every separate copy of the table costs its own LUTs, about 45 for the font plus the logic that picks one bit out of the 35.

The problem

The first version used a block called text_layer: one block per line of text, each with its own copy of the font. The game has 12 lines of text (9 in tetris_render: NEXT, LEVEL, LINES, the line count, RIVAL, LINKED, PRESS START, WIN!/LOSE/DRAW, GAME OVER; and 3 in chaos_render: two task-panel lines and the banner). That's 12 copies of the same table.

When the media layer was added, the first full build used 7,566 LUTs (95 %) and Vivado could not place it: the chip was too full to fit the parts in and wire them together.

The idea

The screen draws one pixel at a time, and one pixel can only be on one line of text at a time. So at any moment only one character is being looked at, and one copy of the font is enough.

text_multi does it in two parts, both within the same clock:

  1. Which line, which letter, which dot. For every line k it checks "is (x, y) inside line k's box?". That's only cheap comparisons against the line's corner (X0S, Y0S), its length (LENS) and size (SHIFTS: each font dot is 2SHIFT screen pixels). For the line that matches, it works out the character number ci = dx / 6 (a letter is 5 dots plus 1 gap), the column inside it cc = dx mod 6 and the row dy, then picks that character's 6-bit code.
  2. Look the code up once. glyph_of(code) gives the 35 bits, and bit 5·dy + cc is the answer: lit or not. The result goes out on pix(k), one bit per line, so tetris_render still knows which line it was and can colour it.

The comparisons per line remain (they are small), but the big table now exists once per renderer: 2 copies instead of 12. Together with a second fix (moving the bouncing balls one per clock instead of all at once) the build dropped to 6,972 LUTs and placed. The final game is 6,797 LUTs (85 %).

A for loop in VHDL is not a loop in time. Vivado copies its body once per line, so all 9 comparisons are separate circuits working at the same moment. Only the font look-up after the loop exists once.

part 2 · sim/ and tools/sim.bat

Testbenches: testing a circuit without a board

What simulation is

A simulator is a program that pretends to be the chip. It reads the same VHDL and works out the value of every signal at every moment: every clock edge, every flip-flop, every wire. Nothing goes near the board. We use xsim, the simulator inside Vivado.

Why bother: building a .bit takes minutes, and on the board you only see the end result. In simulation a run takes seconds, you can see inside every module, and you can set up exact situations (a bouncy switch, a cable that sends garbage at the worst moment) on purpose, every time.

What a testbench is

A testbench is a VHDL file that never goes on the board. It is the pretend world around the design. It has no ports (nothing outside it), and inside it:

  • makes the clock: clk <= not clk after 10 ns; flips every 10 ns, so 20 ns per cycle = 50 MHz, like the board's crystal
  • places the design being tested: the same u_x : entity work.name port map (...) as in top_tetris
  • drives the inputs in a process, written like a script: "wait 200 ns, set start to 1, wait one clock, ..." (wait only works in simulation; real hardware can't wait)
  • checks the outputs and prints with report. A wrong answer is reported with severity error, and the last line says TEST PASSED or TEST FAILED

The smallest one, line by line: tb_uart_loop

It checks uart_tx and uart_rx by wiring the sender's output straight into the receiver ("loopback") and sending 6 bytes.

Try it: what the wire carries for one byte

The line rests at 1. A 0 "start bit" says "a byte is coming", then the 8 data bits go out lowest bit first, then a 1 "stop bit". uart_rx waits half a bit after the start edge and then samples every 434 clocks (the dots), right in the middle of each bit where the value is steadiest.

How a simulation is run: tools\sim.bat

  1. xvhdl -prj sim\tb_uart_loop.prj: compile. The .prj file lists the VHDL files in order (packages first, the testbench last). This is where typing mistakes show up.
  2. xelab tb_uart_loop: elaborate. Connect all the pieces into one model starting from the testbench, a "snapshot" ready to run.
  3. xsim ... -runall: run until nothing is left to happen. That's why every testbench stops its clock at the end; a clock that never stops would run forever. It's also why testbenches of the whole game set USE_STARTUP => false: Xilinx's simulation model of STARTUPE2 never goes quiet.

How I "read" a simulation

There's a waveform viewer in Vivado, but every testbench here is self-checking: it decides PASS or FAIL itself, so the result can be read as text. There are three kinds of evidence:

1 · report lines

The testbench knows the right answer and compares. Example: tb_versus wires two boards together and checks that START on A starts B, that garbage sent by one arrives at the other, that one ends on WIN and the other on LOSE, and that a start press during the 1.5 s cool-down is ignored.

2 · golden files

For the media, the right answer is too big to write by hand. So Python builds a tiny media file (sim/game_sim.hex, one byte per line) and decodes it with its own Python decoder into game_sim_expect.txt. The testbench feeds the hex file to the circuit and compares its sound samples and pixel colours with the expect file, number by number, using VHDL's file reading (textio). Two independent decoders agreeing is strong evidence both are right.

3 · screenshots

The frame testbenches watch the VGA pins for a whole frame and write every pixel into a text picture file (frame.ppm: "P3 640 480 15" then three numbers per pixel). tools\ppm2png.py turns it into a PNG, and I look at it. The screenshots in the design document came from here, not from a camera.

Tricks the testbenches use

  • Speeding up time. A real frame is 833,333 clocks. tb_tetris_core makes the frame tick come every 200 clocks, and tb_versus runs the link at 8 clocks per bit, through generics, so a whole game takes under a second of simulation. The logic is unchanged; only the constants differ.
  • Robot players. tb_tetris_core has a robot that tries every rotation and column for each piece and presses the buttons like a person. tb_chaos has a "solver" that moves the 8 task switches to finish tasks.
  • Pretend parts. sim/flash_model.vhd pretends to be the board's flash chip (S25FL064L). It answers the ID command 9F with 01 60 17 and the READ command 03 with bytes from the hex file. It is deliberately a bit slower than the real chip (15 ns instead of 8 ns), so the design is tested with some margin.
  • Nasty inputs on purpose. tb_switch_filter makes a switch bounce randomly between 0 and 1 for 3 sample periods on every flip, then checks the output changed exactly once per flip.

part 3 · src/media/media_mix.vhd

Jevil's sine path

When the Jevil attack hits, he floats around the whole screen in a looping, never-quite-repeating curve. That curve is two sine waves, one moving him left-right and one moving him up-down:

x = 272 + 230 · sin(2π t / 6.1 s)
y = 190 + 150 · sin(2π t / 3.7 s + 0.6)

Where every number comes from

numbermeaningwhy this value
272, 190the middle of his path (his top-left corner)He is 96 × 100 on screen (48 × 50 pixels drawn 2×). Centred: (640 − 96) / 2 = 272 and (480 − 100) / 2 = 190.
230how far he swings left and rightx goes from about 272 − 230 = 42 to 272 + 230 = 502, and 502 + 96 = 598 < 640: he never leaves the screen. (The circuit's whole-number maths actually reaches 43 to 501.)
150how far he swings up and downy goes from about 40 to 340 (really 41 to 339), and 340 + 100 = 440 < 480.
6.1 s, 3.7 show long one full swing takesTwo different speeds that don't divide evenly, so the path takes a long time to repeat. This is called a Lissajous curve. With equal speeds he would just go round one circle or line.
0.6a head start for the y wave, in radiansSo he doesn't start on a straight diagonal: the two waves are out of step from the first frame.

How the hardware does sin() without a calculator

An FPGA has no sin button. The circuit uses three tricks.

  1. The angle is a 16-bit counter. 0 to 65,535 stands for one full turn (0 to 2π). Each frame the x angle grows by 179 and the y angle by 295. When a 16-bit number goes past 65,535 it wraps back to 0 by itself, just like an angle wrapping past 360°. So "going round the circle forever" costs nothing.
    One turn of x: 65,536 / 179 = 366 frames, and at 59.52 frames a second that's 6.1 s. One turn of y: 65,536 / 295 = 222 frames = 3.7 s. The y angle starts at 6,258, which is 0.6 rad × 65,536 / 2π.
  2. A table of a quarter of a sine wave. A sine wave is made of 4 mirror-image quarters, so the circuit stores only the first quarter: 128 numbers from 0 to 255, Q(k) = round(255 · sin(2π (k + 0.5) / 512)). The top 2 bits of the angle say which quarter, the next 7 bits pick one of the 128 entries, and the lowest 7 bits are ignored (too fine to matter):
    • quarter 0: Q(k) (rising)
    • quarter 1: Q(127 − k) (the table read backwards: falling)
    • quarter 2: −Q(k)
    • quarter 3: −Q(127 − k)
    The + 0.5 samples the middle of each slot, so a quarter read backwards fits exactly against the one read forwards.
  3. Scale with a multiply and a shift. The table gives −255 to +255, which is almost "sine × 256". So jx = 272 + 230 × sv / 256, and dividing by 256 is just dropping 8 bits. The multiply uses one of the chip's DSP blocks (hardware multipliers), the one listed for media_mix in the resource table.

How it advances. Nothing moves between frames. Once per frame, at frame_tick, a 3-step sequence runs, one step per clock: step 0 adds 179 and 295 to the angles and looks up sin for x; step 1 computes jx and looks up sin for y; step 2 computes jy. Doing x and y one after the other lets them share one table and one multiplier. Every 4th frame pbase moves to the next of his 8 poses (pose × 2,400, since one pose is 48 × 50 = 2,400 pixels), which makes him flap at 15 poses a second.

Drawing him. For every screen pixel inside his 96 × 100 box, the circuit asks media_engine for the pixel pbase + (dy / 2) × 48 + dx / 2. The "/ 2" makes each of his pixels 2 × 2 on screen, and × 48 is done as × 32 + × 16 (two shifts and an add), so no second multiplier is needed.

part 4 · tools/

The computer side: what every script does

The FPGA runs the game, but the PC prepares everything it needs: the circuit file, the media file, and the test data. Python is used where the job is "read some files, do maths, write a file". Batch files (.bat) just run other programs in the right order with the right options.

The libraries, in one line each

  • numpy: maths on big arrays at once (a whole video frame of pixels, a whole song of samples)
  • Pillow: open and save pictures, resize, convert colours
  • ffmpeg: a separate program the scripts call to decode any video or audio file into raw pixels and samples
  • struct: turns numbers into exact bytes, e.g. struct.pack('<H', 1104) → 50 04 (the < means little-endian: low byte first)
  • pyserial: talks to a COM port, here the board's USB-serial chip
  • argparse: reads options typed after the script name, like --sim

part 5 · src/game/tetris_core.vhd + versus_link.vhd

Win, lose and draw: a race measured in microseconds

Each board runs its own game and decides its own result. Nobody is in charge, and there is no "DRAW" message. The two boards still always agree, because both follow the same three rules.

The three rules

  1. I top out → I show LOSE and tell the other board. Topping out happens in two places in tetris_core: a new piece has no room to appear (S_SPAWN_CHK), or incoming garbage pushes a block out of the top row (S_GARB). In the same clock the board stops playing, sets result = LOSE, sends a one-clock lost_o pulse to the link, and starts a stopwatch: lose_age := 0. From then on lose_age goes up by 1 at every frame tick (60 a second) and stops at 63.
  2. The link sends a LOST byte as soon as the wire is free. versus_link remembers the request (lost_p). If the transmitter is in the middle of another byte (usually a heartbeat), LOST waits for it to finish. When several messages wait, the order is START > LOST > ATTACK > GARBAGE > HEARTBEAT.
  3. A LOST byte arrives → decide. If I'm still playing, I WIN (and stop). If I already lost and lose_age < 6, my LOSE becomes DRAW. Otherwise nothing changes.
-- tetris_core.vhd: the other board lost
if opp_lost = '1' then
  if playing_r = '1' then
    result_r  <= R_WIN;                  -- it lost first: I win
    playing_r <= '0';  state <= S_IDLE;
  elsif result_r = R_LOSE and lose_age < 6 then
    result_r  <= R_DRAW;                 -- we both lost at (almost) the same moment
  end if;
end if;

Both boards run this same code. If both topped out, each one gets the other's LOST shortly after its own loss, and each turns its own LOSE into DRAW. They end up agreeing without ever discussing it.

How long everything takes

The link runs at 115,200 bits a second. One bit lasts 434 clocks at 50 MHz = 8.68 µs, and a byte is 10 bits (start + 8 data + stop) = 86.8 µs. The receiver says "valid" in the middle of the stop bit, 9.5 bits = 82.5 µs after the byte starts. One frame of the screen is 16,800 µs. Next to a frame, the message is tiny:

To scale: one frame vs. the LOST message
one frame
LOST, wire free
LOST, worst case
16,800 µs · 82.5 µs · 169 µs (a heartbeat had just started, so LOST waits 86.8 µs first)

So the LOST message always arrives within about 1 % of one frame. That decides everything below.

So when is it really a draw?

Say board A tops out at time 0. Its LOST reaches B 82.5 to 169 µs later. At that moment B is either:

  • still playing → B shows WIN and stops. B can never top out after that, so it never sends LOST, and A stays on LOSE.
  • already topped out (in the last 82.5 to 169 µs) → B is on LOSE with lose_age 0, so B shows DRAW. B's own LOST reaches A just as fast, A's lose_age is 0 too, so A shows DRAW.

A draw needs both boards to top out within about 0.1 ms of each other. If B tops out even 1 ms after A, B has already received A's LOST and won. The 6-frame limit does not make the draw window bigger; it only decides how stale a LOST may be and still count.

Why "lose_age < 6" and not "< 1"?

You guessed the serial line's time is the reason. It's part of it, but the real reason is that lose_age can only count whole frames: it goes up at the frame tick, once every 16.8 ms, whenever that happens to fall.

  • "< 1" would mean "no frame tick has happened since I lost".
  • But A's loss can happen a few µs before one of A's frame ticks (the two boards' frames are not lined up with each other). Then A's lose_age is already 1 by the time B's LOST arrives, 100 µs later. With "< 1", A would stay on LOSE while B shows DRAW: the two screens disagree. Press The "< 1" trap above to see it.
  • The LOST can arrive at most about 0.17 ms after my loss, so at most one frame tick can fall in between. "< 2" is already always safe.
  • 6 frames (0.1 s) is just a comfortable margin. Going bigger changes nothing in real play, because a LOST later than 0.2 ms after my loss can't happen: the other board would have won instead. The limit only protects against a LOST that has nothing to do with my loss.

part 6 · src/common/vga_sync.vhd

How the monitor knows where each pixel goes

The VGA cable carries only five signals that matter: R, G, B (three voltages) and HSYNC, VSYNC (two pulses). There's no clock wire and no pixel address. The monitor still puts every pixel in the right place. Here's how.

1. VGA was made for a beam that never needed a clock

VGA comes from CRT monitors. Inside a CRT, an electron beam sweeps across the glass at a steady speed, left to right, and lights up the spot it hits. How brightly depends only on the voltage on the R/G/B wires at that instant. HSYNC says "this line is done, swing back to the left and drop one line"; VSYNC says "the picture is done, go back to the top".

So there is no such thing as "sending pixel 37". A pixel is just how long we hold one voltage. We change the colour every 40 ns (the 25 MHz pixel rate), and because the beam moves steadily, 640 changes make 640 dots across one line. The swing back takes time, which is why each line and each frame have invisible "porch" and "sync" time at the end. During that time the colour must be black.

So HSYNC comes 1 / 32.0 µs = 31,250 times a second, and VSYNC 1 / 16.8 ms = 59.52 times a second. (That 59.52 is also the number in Jevil's timing.) vga_sync is just two counters: x counts 0 to 799 on every pixel tick, and when it wraps, y counts 0 to 524.

2. How 4 bits become a colour

Each colour is 4 bits from the FPGA. The board turns those 4 pins into one voltage with a few resistors (a tiny digital-to-analog converter), from 0 V for 0 to about 0.7 V for 15. That gives 16 levels per colour and 16 × 16 × 16 = 4,096 colours. The monitor sees only that voltage; it has no idea bits were involved.

3. How a flat screen finds the pixels again

An LCD has a fixed grid of real pixels, so it can't just "glow wherever the beam is". It has to measure the voltage at exactly the right moments. It works the clock out from HSYNC:

  1. Recognise the mode. It measures how often HSYNC and VSYNC come (31.25 kHz, 59.52 Hz), how many lines there are per frame (525) and which way the pulses go (both active-low). That pattern matches the standard 640 × 480 at 60 Hz mode, so it knows a line has 800 pixel times.
  2. Rebuild the pixel clock. A circuit called a PLL makes a clock that ticks exactly 800 times between two HSYNC pulses. That's our 25 MHz, rebuilt from HSYNC alone. HSYNC is the clock, just 800 times slower.
  3. Sample at the right moment. It knows the picture starts 96 + 48 = 144 ticks after the HSYNC edge. Then it reads the voltage once per tick, 640 times, into its 640 pixels. The "Auto adjust" button on a monitor fine-tunes where inside each 40 ns it reads (the "phase"), so it doesn't read while the voltage is still changing between two pixels.
Try it: what the monitor reads from one line

Two things to try. Move the phase close to 0: the samples land on the edges between pixels, while the voltage is still changing, and the sharp detail goes wrong. That's the shimmer you see before pressing "Auto adjust". Then pick 804 ticks: the monitor still divides the line into 800, so every sample lands a little later than the one before. The start of the line is fine, but by the end it's reading the wrong pixels. That's why vga_sync has to count exactly 800 every line.

What this means for our VHDL

  • Exact counts, every line. The monitor counts along with us. 800 per line and 525 per frame, always.
  • Black outside the 640 × 480 area. The monitor uses the blank time to measure what "black" is. That's why every renderer outputs colour only when video_on = '1'.
  • Colour and sync must stay lined up. tetris_render takes 2 clocks to work out a pixel's colour (the pipeline), and it passes HSYNC, VSYNC and video_on through the same 2 registers, so the colour for pixel x leaves the chip at the same moment as the sync timing for pixel x. If they were off by one, the whole picture would shift by one pixel.
  • 25 MHz instead of 25.175 MHz. The standard says 25.175 MHz. We use exactly half of the board's 50 MHz instead, so no special clock is needed; it is 0.7 % slower. The monitor doesn't care about the exact speed, only that HSYNC comes at a steady rate it recognises; its PLL locks onto whatever we send, and every monitor we tried accepts it.
