tetris_pkg · xpos_t, SPAWN_XWhere is the piece? Wide columns

The playfield is 10 columns. The core numbers them on a 16-column ruler: 3 imaginary wall columns on each side. Top numbers = wide column (what cur_x uses). Bottom numbers = real board column. Wide = board + 3, always.

The piece's position (x, y) is the top-left corner of its dashed 4×4 box, not of the coloured blocks. Move the box around, into the walls too: red blocks are where collides() finds a hit.

piece
wall / floor ('1' in the collision check) the 4 columns under the box block that collides
"Top-left is 6, so why columns 3–6?"6 is on the wide ruler. Wide column 6 is board column 3. The box is 4 wide, so it covers wide 6–9 = board 3–6. The T fills board 3–5, and the box's 4th column (board 6) is empty.
Why add wall columns at all?The check turns each box row into a 16-bit vector "111" & occ(row) & "111". Vector bits are numbered from 0, never negative. Boxes hang past the wall: a vertical I against the left wall has its box at board −2. With the extra 3 columns that's wide 1, and the wall is just '1' bits, so no special wall code is needed.
Why −2..14, not −3..12?That's only the range of the integer type, i.e. how many bits the register gets. It isn't the play area. Real positions are about x = 1..11 (see "legal x" on the right). The core also tests spots that may be illegal: moving tries ±1, a wall kick tries ±2. So test positions reach about −1..13. −2..14 covers that with a little spare. ypos_t (−2..21) is the same idea for rows.

tetris_core · collides()How the collision check sees it

The same box as above, taken apart the way collides() does it. For each box row r it builds the 16-bit wide row. Then for each box column c with a block it looks at wide(x + c). Any '1' under a block means a hit, and collide is the OR of all of them. Move the piece in section 1 and this updates.

tetris_core · state_tOne frame through the state machine

Each box is a when S_… => in the code. Each step below is one clock (20 ns). Pick a situation and step through it. The highlighted box is the state the machine is in during that clock. Every arrow is a possible change of state (the four states on the right are new for versus garbage and the chaos SINK bonus). Dashed arrows are the "nothing to do, skip" paths. A curved arrow back into the same box means the state repeats for several clocks. Follow it from the top: a new piece flows down the middle into S_GHOST; the frame loop goes round the left and bottom; locking goes up the right side back to S_PICK.

tetris_core · S_LOCK, placed_row()Writing the piece into the field

When the piece locks, S_LOCK runs for 4 clocks, one per box row (lock_r = 0..3). Each clock it takes one row of the 4×4 box, slides it to the right board columns with placed_row(), and ORs it into that field row. This uses the piece from section 1, dropped to where it would land.

placed_row asks for every board column c: which box column is above me? The answer is j = c + 3 − x. If j is 0..3 the column is under the box and takes shape bit sh(4·r + j). Otherwise it gets 0.

Columns are shown left = 0 like on screen. (In VHDL the vector is written 9 downto 0, so the same row printed as a string has column 0 on the right.)

tetris_core · S_CLEARRemoving full rows with two pointers

rd (read) visits every row from the bottom up, one per clock. wr (write) is where the next row that stays goes. A full row is skipped, not copied. That makes wr fall behind rd, so everything above slides down. When rd runs off the top, the rows from wr up are emptied. The example has full rows at 14, 16 and 19.

tetris_core · bcd_inc()Adding 1 in BCD

The line counter is stored as BCD: 16 bits = 4 decimal digits, 4 bits each. The 7-segment display can then show each digit directly, with no binary-to-decimal converter. bcd_inc adds 1 like you would on paper: start at the lowest digit; a 9 becomes 0 and carries to the next digit; anything else gets +1 and the carry stops.

tetris_core · lfsr, S_PICKRandom pieces: LFSR and the 7-bag

The LFSR shifts left every clock. The new bit 0 is bit15 xor bit13 xor bit12 xor bit10 (the highlighted taps). It runs through all 65,535 non-zero patterns before repeating. S_PICK reads its lowest 3 bits as a number 0..7. It accepts the number only if it's 0..6 and that piece hasn't been dealt from the current bag. Otherwise it waits one clock (new LFSR value) and tries again.

tetris_render · stage 1 + 2From pixel to colour

The screen is never stored anywhere. For each pixel, the renderer works out which cell it falls in, reads that cell, checks whether the piece or ghost covers it, and picks a colour. versus_link · msg()One byte between the boards

Every message is one byte: 3 bits of type, 5 bits of value. uart_tx then sends it as 10 bits on the wire: a 0 start bit, the 8 data bits lowest bit first, and a 1 stop bit. Each bit lasts 434 clocks (8.68 µs). Pick a message and watch the wire.

tetris_core · S_ATTACK, S_GARBGarbage: cancel, send, rise

When a piece locks, S_ATTACK turns the lines it cleared into an attack (2 → 1, 3 → 2, 4 → 4). The attack first cancels garbage waiting for you (the red meter), and only the rest is sent. If the piece cleared nothing, up to 8 waiting lines come in now. S_GARB then pushes the whole field up one row per clock and adds a grey row with one hole.

tetris_sound · mixerTwo sounds, one pin: the bucket trick

The problem. An FPGA pin is a switch: it is either 0 V or 3.3 V, nothing in between. Flipping it 440 times a second gives a 440 Hz beep at full volume. That's fine for one sound, but we want two sounds at once (music + effect), and the music quieter. Both need voltages between 0 and 3.3 V.

The trick. Flip the pin on and off millions of times a second. A headphone's speaker can't move that fast, so it only follows the average. A pin that is on 3 clocks out of every 16 pushes the speaker like a steady 3/16 × 3.3 V ≈ 0.6 V. It's the same as dimming an LED by blinking it too fast to see.

The mixer does this in two steps: (1) decide how loud the pin should be right now, a number called loudness from 0 to 15 (out of 16). (2) a tiny circuit, the bucket, decides on each clock whether the pin is on, so that on average it's on loudness clocks out of 16. That second part is what's called a sigma-delta modulator.

Step 1 · how loud right now?

Each sound is a square wave, so at any instant it is either up (1) or down (0). Music adds 3, the effect adds 7 (louder). Press to change what each square is doing at this instant.

Step 2 · the bucket, one clock at a time

Every clock, pour loudness into a bucket that holds 16. If it reaches 16 or more, it overflows: the pin is ON for that clock and 16 is poured away. Otherwise the pin is OFF. Step through it: over every 16 clocks the bucket overflows exactly loudness times.

In the VHDL the bucket is a 5-bit register: bits 3..0 hold what's in it (0..15) and bit 4 means "it overflowed". bucket <= ('0' & bucket(3 downto 0)) + loudness; keeps the 4 low bits (dropping bit 4 = pouring the 16 away) and adds the new loudness. audio <= bucket(4); is the pin. The name: Σ (sigma, "sum") because it keeps adding; Δ (delta, "difference") because each overflow takes 16 back out, so it never drifts away from the right average.

Step 3 · zoom out: what the headphones get

6 milliseconds of sound. The two square waves go up and down hundreds of times a second; loudness follows them (0, 3, 7 or 10). At this zoom the pin's on/off flicker is far too fast to draw (one clock is 20 ns, 300,000 clocks fit in this picture), so the bottom graph shows what the speaker actually feels: the average, loudness/16 × 3.3 V. That stepped wave is the music and the effect added together.

chaos_task · chaos_renderTry the chaos tasks

This panel runs the same rules as chaos_task.vhd at 60 frames a second, and draws the same panel as chaos_render.vhd. Click the switches below (SW13 on the left, like the panel) to do the task. "press a button" stands for any Tetris button (it matters for HANDS). On the board you'd be doing this while playing Tetris. Every length of time (time allowed, HANDS / HOLD goal, zone width, marker speed) is picked at random from its range each time you press "new task", like rand_range does in hardware. In the game the panel only appears when a task starts; between tasks the screen just says CHAOS MODE ON.

chaos_pkg · chaos_renderHow the cat spins with only one picture

The OIIA cat is one 16 × 16 picture in a ROM (3 bits per pixel: see-through, black, grey, white, pink), drawn 4× bigger (64 × 64). A real 3D spin would need many pictures. Instead chaos_render cycles through 4 ways of reading the same picture, 8 frames each. Normal → squeezed → mirrored → squeezed looks like a card turning around.
